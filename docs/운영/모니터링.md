# 오류 수집과 업타임 알림 (#185)

결정기록 D-149. 오류는 Sentry, 살아 있는지는 UptimeRobot 이 본다. 둘 다 무료 플랜이고 알림은 운영자 메일로 온다.

## 업타임 (UptimeRobot, 코드 밖)

| 모니터 | 주소 | 주기 | 알림 |
|--------|------|------|------|
| API | `https://api.whenwemeet.day/v1/health` | 5분 | 운영자 메일 |
| 웹 | `https://whenwemeet.day` | 5분 | 운영자 메일 |

- API health 는 DB `SELECT 1` 까지 확인한다 (실패 시 503 `DB_UNAVAILABLE`, [배포.md](./배포.md) "운영 점검 결과"). 그래서 API 모니터 하나로 API 와 DB 를 같이 본다.
- 모니터 추가, 알림 대상 변경은 UptimeRobot 대시보드에서 한다. 저장소에 설정이 없다.

## 오류 수집 (Sentry)

| 항목 | 값 |
|------|----|
| 조직 | `personal-km5` |
| 프로젝트 | `whenwemeet-api` (NestJS), `whenwemeet-web` (Next.js) |
| 플랜 | Developer(무료), 오류 월 5천 건 |
| 보내는 것 | **오류만**. 트레이싱, 프로파일링, 세션 리플레이, 로그, 세션 집계는 켜지 않는다 |
| 소스맵 업로드 | 하지 않는다 (인증 토큰 없음). 빌드에 `SENTRY_AUTH_TOKEN` 이 필요 없다 |
| 앱 셸 (Expo) | 범위 밖. 셸 안의 웹 화면 오류는 웹 프로젝트로 들어온다 |

### 환경 변수 (값은 각 플랫폼 시크릿에만, DSN 을 저장소와 문서에 쓰지 않는다)

| 곳 | 이름 | 값 |
|----|------|----|
| Railway (API) | `SENTRY_DSN` | `whenwemeet-api` 프로젝트의 DSN |
| Railway (API) | `SENTRY_ENVIRONMENT` | 선택. 없으면 `NODE_ENV` (운영 이미지는 `production`) |
| Vercel (웹) Production | `NEXT_PUBLIC_SENTRY_DSN` | `whenwemeet-web` 프로젝트의 DSN (브라우저용, 빌드 때 박힘) |
| Vercel (웹) Production | `SENTRY_DSN` | 위와 같은 값 (route handler, 서버 컴포넌트용) |
| Vercel (웹) | `SENTRY_ENVIRONMENT` | 선택. 없으면 `VERCEL_ENV`, 그다음 `NODE_ENV` |

- DSN 이 비면 SDK 를 아예 띄우지 않는다. 로컬, 테스트, CI 는 비워 둔다.
- 릴리스는 커밋 SHA 다. API 는 SDK 가 `RAILWAY_GIT_COMMIT_SHA` 를, 웹은 빌드 때 `VERCEL_GIT_COMMIT_SHA` 를 쓴다. 따로 넣지 않는다.
- `NEXT_PUBLIC_SENTRY_DSN` 은 빌드 때 번들에 들어가므로 값을 바꾸면 **재배포**해야 한다.
- API 의 SDK 는 Nest 보다 먼저 뜬다 (`apps/api/src/instrument.ts`). 그래서 로컬 `.env` 의 `SENTRY_DSN` 은 읽지 않는다(ConfigModule 이 나중에 읽음). 로컬에서 보내 보려면 셸에서 `SENTRY_DSN=... pnpm start:dev`.

### 무엇을 보내나

| 앱 | 보냄 | 보내지 않음 |
|----|------|-------------|
| API | 예외 필터까지 온 5xx (처리 못 한 예외, `INTERNAL`, `KAKAO_ERROR`, `APPLE_ERROR`), 푸시 틱 실패(태그 `where=push.tick`), 처리 안 된 rejection | 4xx `ApiException` 전부, 설정 없음 503 (`*_NOT_CONFIGURED`), health 의 `DB_UNAVAILABLE` (업타임이 본다) |
| 웹 | 서버 컴포넌트, route handler, proxy 의 오류 (`onRequestError`), 브라우저 렌더 오류(`error.tsx`, `global-error.tsx`), 브라우저 전역 오류 | 서버에서 난 렌더 오류를 브라우저 경계가 다시 보내는 것(`digest` 있으면 건너뜀) |

### 거르는 것 (개인정보)

SDK 수집 단계(`dataCollection`)에서 끄고, `beforeSend`, `beforeBreadcrumb` 에서 한 번 더 지운다 (`apps/api/src/monitoring/sentry-scrub.ts`, 웹 사본 `apps/web/src/lib/sentry-scrub.ts`).

- 쿠키, 요청 본문, 응답 헤더, 접속 IP(`env`)는 버린다. 요청 헤더는 `accept`, `accept-language`, `content-length`, `content-type`, `host`, `user-agent` 만 남긴다 (Authorization, X-Internal-Key, X-Client-IP, X-Forwarded-For 등은 전부 버림)
- 쿼리에서 이름에 `token`, `code`, `email`, `key`, `secret`, `password`, `state`, `session`, `signature`, `auth`, `ticket` 이 들어간 값은 `[Filtered]` (키는 남김). 이메일 링크 토큰, handoff 코드, OAuth code/state 가 여기 걸린다
- 경로의 초대코드 `/join/<코드>`, `/invites/<코드>` 는 `[Filtered]`
- 메시지, 예외 문구, 브레드크럼, extra 안의 이메일, `Bearer ...`, JWT 꼴 문자열, `token=...` 꼴 값은 `[Filtered]`
- 사용자 정보는 내부 id 만 남기고 이메일, IP, 이름은 버린다 (지금은 user 를 넣지 않는다). 브라우저 콘솔 브레드크럼의 인자는 버린다
- 스택 프레임의 지역 변수는 수집하지 않는다. 프레임의 소스 줄(우리 코드)은 남는다

Sentry 프로젝트 설정에서도 **Security & Privacy > Prevent Storing of IP Addresses** 를 켠다 (두 프로젝트 모두, 서버 쪽 IP 추론까지 막음).

### 운영에서 확인

- 운영 서버에 시험용 오류 엔드포인트는 두지 않는다. DSN 이 맞는지는 로컬에서 시험 이벤트 하나를 보내 본다 (환경 `test` 라 운영 이슈와 섞이지 않는다). 웹 프로젝트도 DSN 만 바꿔 같은 명령으로 확인한다

  ```bash
  cd apps/api
  SENTRY_DSN='<프로젝트 DSN>' node --input-type=module -e "import * as S from '@sentry/nestjs'; S.init({ dsn: process.env.SENTRY_DSN, environment: 'test' }); S.captureException(new Error('sentry 연결 확인')); await S.flush(5000);"
  ```

- 이벤트가 0건인 것은 정상일 수 있다. 실제 수집 경로는 배포 후 Railway, Vercel 로그의 5xx 와 Sentry 이슈를 맞춰 본다
- 무료 한도(월 5천 건)가 차면 그 달은 버려진다. 같은 오류가 폭주하면 Sentry 의 이슈에서 **Ignore** 나 **Spike protection** 으로 막는다
