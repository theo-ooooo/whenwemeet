# 이메일 로그인 운영 (#245)

설계는 [`docs/설계/이메일-로그인.md`](../설계/이메일-로그인.md) (D-110 ~ D-120). 이 문서는 켜기, 점검, 지표 쿼리만 둔다. 변수 목록은 [배포.md](./배포.md) "API" 와 "웹" 표. Resend 도메인 인증(DNS 레코드)은 설계 9-1 절차 그대로.

## 구조 한 줄
웹 route handler 가 `X-Internal-Key`, `X-Client-IP` 를 실어 `POST /v1/auth/email/*` 를 부른다 → API 가 `EmailLoginChallenge` 행(메일 1통 = 1행, 해시만)을 넣고 Resend `POST /emails` 로 링크와 6자리 코드를 보낸다(10초, 재시도 없음). 횟수 제한(이메일 60초 1번, 1시간 5번, IP 1시간 20번)도 이 행 수로 센다. 행은 30일 뒤 요청 때 지워진다.

## 켜는 순서
1. Resend 도메인 `whenwemeet.day` Verified, Click/Open tracking 끔 (설계 9-1)
2. API 배포 (마이그레이션 `email_login` 포함). 스위치가 없으면 `/v1/auth/email/*` 는 전부 503 `EMAIL_NOT_CONFIGURED`
3. Railway `api` 변수: `RESEND_API_KEY`, `INTERNAL_API_KEY`(`openssl rand -hex 32`), `REVIEW_EMAIL`, `REVIEW_CODE` → 마지막에 `EMAIL_LOGIN_ENABLED=1` → 재배포
4. 확인: 기동 로그에 `[EmailLogin] 심사 계정 꺼짐` 이 **없어야** 한다(있으면 `REVIEW_*` 값 확인). 키 없이 부르면 403 이어야 한다:
   ```bash
   curl -s -X POST https://api.whenwemeet.day/v1/auth/email/link/inspect -H 'Content-Type: application/json' -d '{"token":"x"}'
   # {"status":403,...,"error":{"code":"FORBIDDEN"}}  (503 이면 스위치나 키가 비었다)
   ```
5. 웹 배포 → Vercel Production 변수 `INTERNAL_API_KEY`(API 와 같은 값), `EMAIL_LOGIN_ENABLED=1` → 재배포(버튼 노출)
6. 개인 메일함(Gmail, 네이버 중 하나 이상)으로 실제 로그인 한 번, 스팸함 여부 확인
7. 셸 `eas update` (설계 7장)

끄기(응급): Vercel `EMAIL_LOGIN_ENABLED` 부터 지운다(버튼이 사라짐) → 필요하면 Railway 것도 지운다.

## 로그 (`[EmailLogin]`)
이메일 전체, 토큰, 코드, 가입 티켓, IP 원문은 남기지 않는다 (설계 9-3).

| 줄 | 뜻 | 조치 |
|----|----|------|
| `request challengeId=12 domain=gmail.com review=false sendStatus=SENT ms=420` | 발송 접수 | - |
| `request ... sendStatus=FAILED http=422 error=validation_error` (warn) | Resend 가 거절. 사용자 화면은 같은 "메일을 보냈어요" | `error` 가 `validation_error`(주소 문제), `rate_limit_exceeded`, `daily_quota_exceeded`(무료 하루 100통) 인지 확인 |
| `request ... sendStatus=FAILED http=401 error=...` 또는 `403` | 키가 틀리거나 도메인 미인증 | Railway `RESEND_API_KEY`, Resend 도메인 상태 |
| `request ... sendStatus=FAILED http=- error=TIMEOUT` / `CONNECTION` | 10초 안에 응답 없음, 연결 실패 | 잦으면 Resend 상태 페이지 |
| `request ... review=true sendStatus=SKIPPED` | 심사 계정 (메일 안 보냄) | - |
| `verify challengeId=12 via=LINK result=SESSION` / `SIGNUP` / `EMAIL_CODE_INVALID` 등 | 링크, 코드 검증 결과 | `EMAIL_CODE_LOCKED` 가 한 이메일에 반복되면 남이 코드를 찍는 중일 수 있다 (설계 14장) |
| `심사 계정 꺼짐 (...)` (warn, 기동 때) | `REVIEW_EMAIL`, `REVIEW_CODE` 가 비었거나 코드가 6자리 숫자가 아님 | 심사 제출 전 값 확인 |

## 점검 쿼리
DB 는 Railway MySQL ([railway.md](./railway.md)). 시각 컬럼은 UTC.

오늘(UTC) 발송 수와 결과. 무료 플랜 하루 100통, 70통을 넘으면 유료 검토 (설계 9-4):
```sql
SELECT sendStatus, COUNT(*) FROM EmailLoginChallenge
WHERE createdAt >= UTC_DATE() AND isReview = 0 GROUP BY sendStatus;
```

최근 실패 (Resend 로그에서 찾을 때는 성공 행의 `providerMessageId`):
```sql
SELECT id, SUBSTRING_INDEX(email, '@', -1) AS domain, createdAt FROM EmailLoginChallenge
WHERE sendStatus = 'FAILED' ORDER BY id DESC LIMIT 20;
```

횟수 제한에 걸리는 IP 해시 (1시간 20통 근처):
```sql
SELECT ipHash, COUNT(*) n FROM EmailLoginChallenge
WHERE createdAt > UTC_TIMESTAMP() - INTERVAL 1 HOUR GROUP BY ipHash HAVING n >= 10 ORDER BY n DESC;
```

## 지표 (기획 7장, 설계 9-4, D-120)
신규 가입 중 이메일 비율 (최근 28일, DEV 제외):
```sql
SELECT provider, COUNT(*) FROM AuthAccount
WHERE createdAt > UTC_TIMESTAMP() - INTERVAL 28 DAY AND provider <> 'DEV' GROUP BY provider;
```

메일 → 로그인 완료율과 링크/코드 비중 (최근 28일, 심사 제외, 접수된 메일만. 행은 30일 보관이라 28일 창):
```sql
SELECT COUNT(*) AS sent,
       SUM(usedAt IS NOT NULL) AS used,
       ROUND(SUM(usedAt IS NOT NULL) / COUNT(*) * 100, 1) AS used_pct,
       SUM(usedVia = 'LINK') AS via_link,
       SUM(usedVia = 'CODE') AS via_code
FROM EmailLoginChallenge
WHERE createdAt > UTC_TIMESTAMP() - INTERVAL 28 DAY AND isReview = 0 AND sendStatus = 'SENT';
```

도착 시간 p95 는 Resend 대시보드 Emails 로그(태그 `type=login`)의 `sent` → `delivered` 로 본다. 웹훅은 들이지 않는다.

## 자주 묻는 것
| 증상 | 확인 |
|------|------|
| "메일이 안 와요" | 위 "최근 실패" 쿼리로 그 도메인의 FAILED 여부 → Resend 로그에서 `providerMessageId` 로 `delivered`/`bounced` 확인. SENT 인데 안 보이면 스팸함 |
| "코드가 만료됐대요" | 15분이 지났거나, 다시 받기를 눌러 이전 메일이 무효가 됐거나, 링크로 이미 로그인했다 |
| 탈퇴한 사용자의 기록 | 탈퇴 트랜잭션이 그 이메일의 행을 모두 지운다. Resend 쪽 로그는 Resend 보관 기간 동안 남는다 |
