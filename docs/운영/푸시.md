# 앱 푸시 운영 (#188)

설계는 [`docs/설계/푸시-알림.md`](../설계/푸시-알림.md) (D-80 ~ D-99). 이 문서는 켜기, 점검, 지표 쿼리만 둔다. 변수 목록은 [배포.md](./배포.md) "API" 표.

## 구조 한 줄
API 프로세스 안 30초 틱이 `SchedulerLease`(행 `push`) 임대를 가진 프로세스 하나에서만 돈다: 예약 계산(일정 알림, 기념일) → 펼치기(받을 기기별 `PushDelivery`) → Expo 발송(100개씩) → 15분 뒤 영수증 → KST 04:00 이후 하루 한 번 30일 지난 기록 삭제. Railway 서비스는 늘리지 않는다 (D-87).

## 켜는 순서
1. API 배포(`PUSH_ENABLED` 없음). 이 상태에서는 일정 변경, 합류 알림 예약 행만 `PushNotification` 에 쌓이고 아무것도 보내지 않는다
2. (권장) expo.dev > 계정 설정 > Access tokens 에서 토큰 생성 → Railway `api` 변수 `EXPO_ACCESS_TOKEN`
3. 그 뒤 expo.dev 프로젝트 설정에서 **Enhanced Security for Push Notifications** 를 켠다. 순서가 바뀌면 토큰 없는 서버 발송이 모두 거절된다 (`HTTP_401` 로 FAILED)
4. 웹 배포 (기기 등록, 설정 화면)
5. Railway `api` 변수 `PUSH_ENABLED=1` → 재배포. 기동 로그에 `push.scheduler 시작 holder=xxxxxxxx` 가 찍히면 켜진 것. 켜기 전에 쌓인 예약 중 10분 넘게 지난 것은 첫 틱에 `SKIPPED` 로 버려진다 (D-88)
6. 앱 1.1 빌드와 심사 (스토어-제출.md)

끄기(응급): `PUSH_ENABLED` 를 지우고 재배포. 예약 행은 계속 쌓이지만 보내지 않는다. 다시 켜면 10분 안 것만 나간다.

## 로그 (`[Push]`)
| 줄 | 뜻 | 조치 |
|----|----|------|
| `push.tick {"planned":..,"weekly":..,"dispatched":..,"skipped":..,"deliveries":..,"cancelled":..,"sent":..,"failed":{..},"requeued":..,"receipts":..,"cleaned":..}` | 일이 있었던 틱 요약 (0건 틱은 debug). (#277) `weekly` 는 그 틱에 만든 주간 예약 수(월요일 09:00 대 틱 한 번), `cancelled` 는 주간 알림을 보내지 않기로 판정한 수 | `failed` 에 코드가 계속 보이면 아래 표 |
| `push.credentials InvalidCredentials IOS ExponentPus` | APNs/FCM 자격 증명 문제 (error). 토큰은 앞 12자만 | `eas credentials` 로 APNs 키, FCM V1 키 확인 |
| `push.send 거절 HTTP_401` | Expo 가 요청 자체를 거절 | `EXPO_ACCESS_TOKEN` 값, 강화 보안 순서 확인 |
| `push.send TIMEOUT` | Expo 응답 없음. 접수됐을 수 있어 다시 보내지 않는다 (D-89) | 잦으면 Expo 상태 페이지 확인 |
| `push.tick 실패 ...` | 틱 예외. 다음 틱에 다시 돈다 | DB 연결, 마이그레이션 확인 |

## 점검 쿼리
DB 는 Railway MySQL (접속 방법은 [railway.md](./railway.md)). 모든 시각 컬럼은 UTC 라 `UTC_TIMESTAMP()` 와 비교한다.

틱이 돌고 있는지 (임대가 30초마다 갱신되고 cursor 가 지금 근처):
```sql
SELECT holder, leaseUntil, cursor, dailyDoneOn, UTC_TIMESTAMP(3) AS now FROM SchedulerLease WHERE name = 'push';
```

최근 하루 예약 상태 (PENDING 이 예약 시각을 1분 넘게 지나 남아 있으면 틱이 멈춘 것):
```sql
SELECT kind, status, COUNT(*) AS n FROM PushNotification
WHERE createdAt >= UTC_TIMESTAMP() - INTERVAL 1 DAY GROUP BY kind, status ORDER BY kind, status;

SELECT id, kind, scheduledAt FROM PushNotification
WHERE status = 'PENDING' AND scheduledAt < UTC_TIMESTAMP() - INTERVAL 1 MINUTE ORDER BY scheduledAt LIMIT 20;
```

발송 결과와 영수증 (FAILED 코드: `DeviceNotRegistered` 앱 삭제, `TIMEOUT` 응답 없음, `EXPIRED` 3번 재시도 실패 또는 10분 지남, `HTTP_4xx` 요청 거절):
```sql
SELECT status, error, COUNT(*) AS n FROM PushDelivery
WHERE createdAt >= UTC_TIMESTAMP() - INTERVAL 1 DAY GROUP BY status, error ORDER BY n DESC;

SELECT receipt, COUNT(*) AS n FROM PushDelivery
WHERE receiptCheckedAt >= UTC_TIMESTAMP() - INTERVAL 1 DAY GROUP BY receipt ORDER BY n DESC;
```

주간 알림 (#277, D-203). 배포 뒤 첫 월요일 09:00 ~ 09:15 KST 에 `push.tick` 로그의 `weekly`(예약), `dispatched`, `cancelled` 를 보고 아래로 확인한다. `weekly` 행의 날짜가 그 월요일이면 그 주 예약을 마친 것:
```sql
SELECT dailyDoneOn FROM SchedulerLease WHERE name = 'weekly';

SELECT status, JSON_UNQUOTE(JSON_EXTRACT(payload, '$.variant')) AS variant, COUNT(*) AS n FROM PushNotification
WHERE kind = 'WEEKLY' AND scheduledAt >= UTC_TIMESTAMP() - INTERVAL 1 DAY GROUP BY status, variant;
```
- 12:00 KST 전에 서버가 돌아오면 그 주 것을 보낸다(3시간 따라잡기). 12:00 넘게 멈췄으면 그 주는 없다(의도)
- 늘 CANCELLED 가 대부분이다: 일정 없는 개인 달력, 깨우기 조건이 아닌 팀, 깨우기를 켠 사람이 없는 팀

## 성공 기준 지표 (기획 7장, 설계 10-3, D-97)

(#277) 주간 요약을 끈 비율과 깨우기를 켠 비율 (기기 있는 사람 중. 출시 4주 뒤 확인, 끈 비율 목표 10% 이하):
```sql
SELECT AVG(u.notifyWeekly = 0) AS weekly_off_rate, AVG(u.notifyWeeklyNudge = 1) AS nudge_on_rate, COUNT(*) AS users
FROM User u WHERE EXISTS (SELECT 1 FROM PushDevice d WHERE d.userId = u.id);
```


권한 허용률 (분모 = 최근 28일 앱 로그인 사용자, 분자 = 그중 기기가 등록된 사용자. 목표 50% 이상):
```sql
SELECT COUNT(DISTINCT d.userId) / COUNT(DISTINCT u.id) AS granted_rate, COUNT(DISTINCT u.id) AS app_users
FROM User u LEFT JOIN PushDevice d ON d.userId = u.id
WHERE u.lastAppLoginAt >= UTC_TIMESTAMP() - INTERVAL 28 DAY;
```

일정 알림 지연 p95 (예정 시각 → Expo 접수 시각, 최근 7일. 목표 60초 이내):
```sql
WITH delays AS (
  SELECT TIMESTAMPDIFF(MICROSECOND, n.scheduledAt, d.sentAt) / 1000000 AS delay_s
  FROM PushDelivery d JOIN PushNotification n ON n.id = d.notificationId
  WHERE n.kind = 'REMINDER' AND d.status = 'SENT' AND d.sentAt >= UTC_TIMESTAMP() - INTERVAL 7 DAY
), ranked AS (
  SELECT delay_s, ROW_NUMBER() OVER (ORDER BY delay_s) AS rn, COUNT(*) OVER () AS cnt FROM delays
)
SELECT delay_s AS p95_seconds, cnt AS samples FROM ranked WHERE rn = CEIL(cnt * 0.95);
```

주간 재방문은 App Store Connect 앱 분석, Play Console 통계의 주간 활성 기기로 본다 (코드 없음).

## 자주 보는 경우
| 증상 | 확인 |
|------|------|
| 아무 알림도 안 온다 | `PUSH_ENABLED=1` 인지, 기동 로그 `push.scheduler 시작`, `SchedulerLease.leaseUntil` 이 갱신되는지 |
| 한 사람만 안 온다 | `PushDevice` 에 그 사람 행이 있는지 (OS 에서 알림을 끄면 웹이 지운다), `User.notify*`, `Membership.notify`, 그 알림의 `PushDelivery.error` |
| 일정 알림만 안 온다 | `Event.reminder`, 한 번짜리는 `remindAt >= reminderSetAt` 인지 (지난 시각으로 저장하면 안 보낸다, D-86) |
| 팀원 변경이 늦다 | 정상. 첫 변경부터 2분 묶음 뒤에 간다 (D-90) |
| 배포 중 두 컨테이너가 겹침 | 임대 하나만 돈다. 겹쳐 돌아도 유일 키(`dedupeKey`, `(notificationId, token)`)로 중복 발송이 없다 (D-89) |

비밀값(`EXPO_ACCESS_TOKEN`, APNs .p8, FCM 서비스 계정 JSON)은 Railway 변수, EAS 자격 증명에만 둔다. 이 문서나 이슈에 쓰지 않는다.
