출시 순서(합의): 웹 먼저 공개 → Google Play 비공개 테스트(12명, 14일) 바로 시작 → iOS 는 TestFlight 확인 후 심사 제출.

`ITSAppUsesNonExemptEncryption: false` 가 `app.config.ts` 에 이미 있다. 업로드한 빌드에 "수출 규정 정보 누락" 경고가 뜨지 않는다. 혹시 물으면 "표준 암호화(HTTPS)만 사용, 면제 대상" 으로 답한다.

## 2. iOS 빌드와 TestFlight

```bash
cd apps/mobile
eas build -p ios --profile production       # 빌드 번호는 EAS 가 올린다 (autoIncrement)
eas submit -p ios --latest                  # App Store Connect API 키는 처음에 EAS 가 만들고 보관
```

1. App Store Connect > TestFlight 에 빌드가 "처리 중" → "테스트 준비 완료" (10~30분)
2. 내부 테스트 그룹에 본인 Apple ID 추가 → TestFlight 앱으로 설치
3. `앱-빌드.md` 11장 확인 목록을 실기기에서 돌린다. 특히 카카오톡 로그인, 애플 로그인, 메모 앱에서 `https://whenwemeet.day/join/<코드>` 탭, 내 정보 > 사진 > 사진 찍기(#149)
4. 이상 없으면 1.6 에서 이 빌드를 고르고 "심사에 추가"

카카오 iOS 플랫폼 등록: 카카오 개발자센터 > 내 애플리케이션 > 앱 설정 > 플랫폼 > iOS 에 번들 ID `day.whenwemeet.app`. 이미 했다면 넘어간다 (설계 앱.md 12장 7번). 빠지면 카카오톡 로그인이 "등록되지 않은 번들 ID" 로 실패한다.

## 3. 심사용 계정

| 스토어 | 심사자 로그인 수단 | 준비 |
|--------|------------------|------|
| App Store | Sign in with Apple (심사자 본인 계정) | 없음. 카카오 계정은 선택 |
| Google Play | **카카오만** (Android 앱은 애플 버튼을 숨긴다, #145) | **카카오 테스트 계정 필수** |

카카오 테스트 계정 만들기 (사용자):
1. 심사 전용 카카오 계정을 새로 만든다 (이메일 가입. 전화번호 인증이 필요하면 본인 번호 사용)
2. 카카오 계정 설정에서 2단계 인증을 끈다. 해외(심사자 위치)에서 처음 로그인하면 추가 인증을 요구할 수 있으니, 심사 기간에는 그 계정의 새 기기 로그인 알림을 확인할 수 있게 둔다
3. 언제볼까에 한 번 로그인해서 팀 "심사용" 을 만들고 일정 3~4개, 기념일 1개를 넣어 둔다 (심사자가 빈 화면을 보지 않게)
4. 계정과 비밀번호는 저장소와 문서에 적지 않고 각 콘솔 입력칸에만 넣는다

카카오톡 앱이 없는 심사 기기에서는 카카오 SDK 가 시스템 브라우저로 카카오 계정 로그인을 띄운다. 이메일과 비밀번호로 로그인된다.

### 3.1 이메일 심사 계정 (#245, 이메일-로그인.md 8-3, D-118)

`EMAIL_LOGIN_ENABLED=1` 로 이메일 로그인을 켠 뒤부터 Google Play 는 카카오 테스트 계정 대신 이메일 심사 계정을 줄 수 있다. 메일함이 없어도 되고 2단계 인증, 해외 로그인 차단이 없다.

준비 (사용자):
1. 심사 이메일 1개(예: `review@whenwemeet.day`)와 6자리 숫자 코드를 정해 Railway `REVIEW_EMAIL`, `REVIEW_CODE` 에만 넣는다. 저장소, 문서, 이 파일에 값을 적지 않는다
2. 운영 웹에서 그 이메일로 로그인 → 닉네임 → 팀 "심사용" 만들기, 일정 3~4개, 기념일 1개
3. 콘솔 입력칸에 값을 넣는다. Play: 앱 액세스 > 로그인 정보. App Store: 1.7 로그인 정보(선택)

콘솔 안내 문구 틀 (값은 콘솔에서 채운다):

```
Sign-in method: Email (no password, no mailbox access needed)
Email: <REVIEW_EMAIL>
Code: <REVIEW_CODE>

1. On the first screen tap "이메일로 계속하기" (Continue with email).
2. Enter the email above and tap "메일 받기" (Send email).
3. On the next screen type the 6-digit code above. You are signed in immediately.
The team "심사용" (Review) already has sample events and an anniversary.
```

- 앱 안에서는 셸 버전에 따라 첫 화면 모양이 다르다: OTA(`EmailLogin/1`)를 받은 셸은 네이티브 로그인 화면 맨 아래, 받지 못한 셸은 웹 선택 화면의 아래 버튼. 문구 "이메일로 계속하기" 는 같다
- 코드는 15분, 5번 틀리면 다시 받기. 심사 기간에 막히면 [다시 보내기] (60초 쿨다운)

### 4.8 첫 AAB 업로드와 Play 앱 서명

```bash
cd apps/mobile
eas build -p android --profile production   # AAB, EAS 업로드 키로 서명
```

1. EAS 빌드 페이지에서 `.aab` 내려받기
2. **첫 업로드는 Play Console 에서 직접** (Google API 는 처음 업로드를 받지 않는다). 4.7 의 비공개 테스트 새 버전에 올린다. 내부 테스트로 먼저 확인하고 싶으면 내부 테스트 트랙에 먼저 올려도 되지만, 14일 시계는 비공개 테스트부터 돈다
3. Play 앱 서명: 기본값 "Google 이 앱 서명 키 생성 및 관리" 그대로
4. 테스트 및 출시 > 설정 > 앱 무결성 > 앱 서명 에서 두 인증서 확인
   - "앱 서명 키 인증서" (Google 이 다시 서명하는 키) SHA-1, SHA-256
   - "업로드 키 인증서" (EAS 키) SHA-1, SHA-256
5. 카카오 개발자센터 > 플랫폼 > Android > 키 해시에 **앱 서명 키 SHA-1 을 Base64 로 바꾼 값** 추가 (업로드 키 해시는 이미 있어야 함)
   ```bash
   echo "<앱 서명 키 SHA-1, AA:BB:.. 형식>" | tr -d ':' | xxd -r -p | openssl base64
   ```
   빠지면 Play 에서 받은 설치본만 카카오 로그인이 KOE009 로 실패한다
6. Vercel 웹 환경 변수 `ANDROID_CERT_SHA256` = `<업로드 키 SHA-256>,<앱 서명 키 SHA-256>` (쉼표 구분, `AA:BB:..` 형식 그대로) → 웹 재배포 → 확인
   ```bash
   curl -s https://whenwemeet.day/.well-known/assetlinks.json     # 지문 2개
   adb shell pm get-app-links day.whenwemeet.app                    # Play 설치본에서 whenwemeet.day: verified
   ```
7. 이후 업로드는 CLI
   ```bash
   eas build -p android --profile production
   eas submit -p android --latest
   ```
   Play 서비스 계정 JSON 을 `eas credentials -p android` 에 한 번 올린다 (저장소에 두지 않음). `eas.json` 의 submit 은 지금 `track: internal`, `releaseStatus: draft` 다. 비공개 테스트 트랙으로 바로 보내려면 `--track alpha` 를 붙이거나(Alpha 트랙 기준) `eas.json` 을 바꾸는 PR 을 낸다 (모바일 에이전트 작업)

### 5.3 다시 만드는 법

스크립트: `scripts/store-shots/` (`shoot.mjs` 캡처, `compose.mjs` 합성). pnpm 워크스페이스 밖이라 그 폴더에서 `npm install` 한다 (playwright-core, sharp). 브라우저는 설치된 Google Chrome 을 쓴다 (`CHROME_PATH` 로 바꿀 수 있음). 데이터는 목 픽스처(`apps/web/src/mocks/fixtures.ts`, 실행한 날 기준 이번 달)라 실제 사용자 정보가 없다. 픽스처는 고치지 않았다.

```bash
cd apps/web && API_MOCK=1 pnpm dev -p 3205          # 목 서버
cd scripts/store-shots && npm install
node shoot.mjs                 # out/raw/<대상>/<n>.png (대상: ios69 ios63 play duoCover duoLand duoPort, 골라서 줄 수 있음)
```

1. `shoot.mjs` 는 목 로그인(`/auth/kakao?next=/`) 뒤 공지 팝업을 닫고(`POST /api/notices/2/dismiss`) 공지를 본 것으로 두고(`POST /api/notices/seen`, 새 공지 띠 없음) 볼까 안내에 동의(`POST /api/me/assistant-consent`)한다. 팀은 `wwm_group=2` 쿠키로 "우리 둘"
2. UA 끝에 `WhenwemeetApp/1.4.0 (ios)` (Play 는 `(android)`) `EmailLogin/1 Widget/1 DeviceCalendar/1` 를 붙인다. 앱 버전을 목 최신(1.4.0)과 같게 둬서 업데이트 안내 띠가 안 나온다. `addInitScript` 로 `window.ReactNativeWebView` 가짜 브리지를 넣어 `pushStatus` 는 `permission: granted` 로, `calendarSyncStatus`, `calendarSyncEnable`, `calendarSync` 는 `apps/web/src/lib/fake-shell.ts` 와 같은 `calendarStatus` 로 답한다 (fake-shell 의 인라인 스크립트는 Chromium 에 따라 안 돌 때가 있어 쓰지 않는다)
3. `deviceScaleFactor: 3`, `isMobile: true`, `colorScheme: light`, `timezoneId: Asia/Seoul`, 뷰포트는 5.1 표의 CSS 크기. 찍기 전에 포커스를 풀고(`blur`) 마우스를 구석으로 옮겨 hover 흔적을 없앤다. 대화 상자가 보이거나(초대 시트는 제외) 가로로 넘치면 경고를 찍는다. Next 개발 표시는 `devIndicators: false` 라 안 나온다
4. 화면별 조작: 3 은 `/assistant` 에서 글을 넣고 "보내기", 4 는 `/me/device-calendar` 에서 스위치를 켠다, 6 은 `/team` 에서 "초대하기" 줄을 눌러 시트를 연다, 듀오 볼까 패널(7)은 홈에서 "AI 볼까" 버튼을 누른 뒤 패널에서 보낸다
5. `compose.mjs` 는 sharp 로 합성한다. Pretendard 는 `apps/mobile/assets/fonts/` 를 fontconfig(`FONTCONFIG_FILE`, `out/fonts.conf`) 에 등록해 SVG 글자로 그린다. 상태 표시줄(9:41, 신호, 와이파이, 배터리)은 캡처 맨 윗줄 색을 바탕으로 그려 위에 붙인다. iPhone 은 v3 6.3" 짜임(화면 폭 900px 기준)을 폭 비율대로 키운 Dynamic Island 테두리, Play 는 단순 테두리와 그림자. 모두 `flatten` + `removeAlpha`, JPEG 는 92 (sRGB, 4:4:4)
6. 듀오 테두리: Apple Design Resources 베젤 PNG 는 저장소에 없으므로(라이선스, 5.4) 그 베젤로 만든 v3 이미지(`docs/store/ios/duo-marketing-v3/`)에서 떼어 낸다. 모든 v3 장에서 같은 자리가 같은 검은색인 곳을 화면 둘레로 보고, 그 안쪽을 화면 구멍으로 잡는다 (바깥 978×1423, 안쪽 1984×1396, 둘 다 화면 비율과 0.1% 안으로 맞음). 구멍 모서리는 위쪽 두 모서리에서 잰 반지름의 둥근 사각형으로 새 화면을 잘라 넣고, 바깥 화면 카메라는 v3 그대로 위에 다시 얹는다. v3 에 있던 화면 모서리가 테두리 밖으로 삐져나온 흰 선은 바탕색으로 지운다. 안쪽 세로는 가로 테두리를 시계 방향으로 90도 돌려 쓴다 (책처럼 펴는 기기를 세운 모양)

## 11. 일정 장소와 일정 검색 (#199), 신고 현황 (2026-11-13)

### 11.1 #199 에서 바뀌는 것
- 새 저장 항목은 **일정 장소**(직접 적은 글자, 또는 장소 검색에서 고를 때 적은 검색어 + 카카오 장소 번호)뿐이다. 카카오가 준 이름, 주소, 좌표는 저장하지 않는다(D-242). 사용자가 일정에 적은 콘텐츠라 기존 분류에 들어간다: Apple "기타 사용자 콘텐츠", Play "캘린더 일정". **새 분류는 추가하지 않는다** (1.5, 4.5 표의 설명만 갱신)
- **위치: 계속 수집 안 함.** 기기 위치(`navigator.geolocation`, 앱 위치 권한)는 쓰지 않는다. 지도에 찍는 좌표는 사용자가 고른 장소를 보일 때 카카오에서 다시 받은 것이고 저장하지 않는다. 앱 셸 변경, 스토어 빌드 없음
- **검색 기록: 계속 수집 안 함.** 일정 검색어는 주소(`/search?q=`)에만 두고 서버, 브라우저 저장소 어디에도 남기지 않는다. 입력 중 장소 검색어는 카카오 장소 검색으로 넘기기만 하고 로그에 남기지 않는다. 고른 장소의 검색어는 일정 장소 값(사용자 콘텐츠)으로 저장한다
- 개인정보처리방침(`/privacy`)에 장소 저장 단락과 "장소 검색과 지도" 단락(카카오 장소 검색, 지도 표시 때 카카오가 받는 접속 정보)을 넣었다. 웹 배포로 반영된다
- 운영 반영 전: `db-backup`(#184) 수동 실행으로 백업 확보 후 마이그레이션 `20261113052443_event_place` (nullable 열 추가만)
