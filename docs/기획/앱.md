# 언제볼까 모바일 앱 기획 (iOS / Android)

- 이슈: #85
- 상태: **기획 승인 2026-11-10** (GATE 1 통과, 9장 추천안 전부 채택). 다음 단계 P1 설계 (#91)
- 작성: 2026-11-10
- 범위: 지금 웹(whenwemeet.day)을 최소 비용으로 스토어 앱으로 내는 방법. MVP 기획(`MVP.md`) 의 기능 범위는 바꾸지 않는다

## 1. 목표와 대상

**목표**: 스토어에서 "언제볼까" 를 검색해 설치할 수 있게 한다. 화면과 기능은 웹을 그대로 쓰고, 웹 배포가 곧 앱 업데이트가 되게 한다.

**왜 앱인가**: 초대받은 사람이 링크를 열고 그다음부터 다시 들어오는 경로가 "카톡 대화방 스크롤" 뿐이다. 홈 화면 아이콘, 카카오톡 앱으로 한 번에 로그인, 링크 탭 시 앱으로 바로 열림이 재방문을 만든다. 푸시는 이번 범위가 아니다 (MVP 제외 유지).

## 2. 핵심 흐름

| # | 유저 스토리 | 완료 기준 |
|---|------------|-----------|
| A1 | 처음 설치한 사용자로서, 카카오톡 앱으로 한 번에 로그인하고 싶다 | 앱 실행 → 카카오 버튼 → 카카오톡 동의 → 달력. 비밀번호 입력 없음 |
| A2 | 초대받은 사람으로서, 카톡의 `whenwemeet.day/join/<code>` 링크를 누르면 앱이 열려 바로 합류하고 싶다 | 앱 설치 상태면 앱에서 열림, 미설치면 웹에서 열림 (지금과 동일) |
| A3 | 팀장으로서, 초대 링크를 휴대폰 공유 시트로 보내고 싶다 | 설정의 "초대 링크 보내기" 가 iOS와 Android 모두 공유 시트를 띄운다 |

## 3. 방식 비교

전제 확인 (`apps/web` 를 읽은 결과): 웹은 **정적 내보내기(static export)가 불가능** 하다. `app/api/[...path]/route.ts` (쿠키를 Bearer 로 바꾸는 프록시), `app/auth/*` route handler 4개, `proxy.ts`, 쿠키를 읽는 서버 컴포넌트(`page.tsx`, `login`, `join/[code]`, `lib/server-api.ts`) 가 모두 서버를 요구한다. 따라서 "앱 안에 웹 파일을 묶어 넣는" 방식은 웹을 SPA + API 직접 호출(Bearer) 로 다시 짜는 것과 같다. 아래 표에서 웹뷰 계열은 모두 **원격 사이트를 띄우는 방식** 을 전제로 한다.

| 방식 | 개발량 | 우리 코드 변경 | 심사 위험 | 유지보수 | 업데이트 |
|------|--------|---------------|-----------|---------|---------|
| ① PWA 만 | 0.5일 | `manifest`, 아이콘, iOS 메타 추가 | 없음 (스토어 미등록) | 최소 | 웹 배포 즉시 |
| ② Capacitor 셸 + 원격 URL (`server.url`) | 3~5일 | 웹: 앱 감지 분기, 딥링크 파일. API: 앱 로그인 엔드포인트. 셸 프로젝트 신규 | 높음. 공식 문서가 `server.url` 을 "운영용 아님" 으로 명시. 화면이 웹뷰 하나뿐이면 4.2 거절 사례 다수 | 중. 카카오 네이티브 로그인 플러그인이 커뮤니티 제작이라 품질 편차 | 웹 부분은 즉시, 셸은 스토어 심사 |
| ③ Capacitor + 정적 번들 | 3~6주 | 웹 전면 재구성(SSR, 프록시, httpOnly 쿠키 제거, Bearer 저장소) | 낮음 | 높음. 웹과 앱이 다른 빌드 | 앱 쪽은 스토어 심사 |
| ④ Android TWA (Bubblewrap) | 1~2일 (Android 만) | ① + `/.well-known/assetlinks.json` | 낮음. Chrome 이 띄우므로 웹 그대로. 단 Play 의 "웹뷰만 있는 앱" 정책 판단은 받는다 | 최소 | 웹 배포 즉시 |
| ⑤ Expo(React Native) 셸 + WebView | 5~8일 | 웹: 앱 감지 분기, 딥링크 파일, `postMessage` 브리지. API: 앱 로그인 엔드포인트 2개 + 애플 로그인. 셸 `apps/mobile` 신규 | 중하. 로그인, 공유, 딥링크, 오프라인 화면이 네이티브라 "웹사이트 재포장" 이 아님을 보이기 쉽다 | 중. Expo SDK 연 1~2회 올림 | 웹 부분은 즉시. 셸 JS 는 EAS Update, 네이티브 변경만 심사 |
| ⑥ 네이티브/RN 전면 재작성 | 2~3개월 | 화면 전부 새로 | 낮음 | 높음. 화면 두 벌 | 스토어 심사 |

정리
- ① 은 지금 바로 해야 할 일이지만 "스토어 앱" 요구를 채우지 못한다. iOS 는 Safari 공유 메뉴에서 "홈 화면에 추가" 를 사용자가 찾아야 한다
- ② 와 ⑤ 는 구조가 같다(원격 웹 + 네이티브 셸). 차이는 원격 URL 이 공식 사용법이냐다. `react-native-webview` 는 원격 페이지를 띄우는 것이 기본 용도이고, Expo 는 애플 로그인(`expo-apple-authentication`), 딥링크, 공유, 햅틱이 공식 모듈로 있다
- ③ 과 ⑥ 은 "간편히" 라는 요구와 맞지 않는다
- ④ 는 Android 만 해결한다. ⑤ 가 지연될 때의 Android 대안으로 남겨둔다

## 4. 반드시 지켜야 할 제약 (2026-11 확인)

### 4.1 Apple 심사 4.2 최소 기능
"repackaged website 를 넘어서는 기능, 콘텐츠, UI" 가 있어야 한다. 4.2.2 는 web clipping 을 명시적으로 거절 대상에 넣는다. 화면 전체가 웹뷰 하나뿐인 앱은 거절 위험이 크다. 대응: 6장의 네이티브 기능을 넣고, 심사 메모에 무엇이 네이티브인지 적는다.

### 4.2 Apple 심사 4.8 로그인 서비스 — 애플 로그인 필수
카카오 같은 제3자 소셜 로그인으로 기본 계정을 만들면, (1) 이름과 이메일만 수집 (2) 이메일 숨기기 가능 (3) 광고용 추적 없음을 만족하는 다른 로그인을 "동등한 선택지" 로 같이 제공해야 한다. 예외 5개(자체 계정만, 대체 마켓, 교육/기업 계정, 정부 전자ID, 특정 제3자 서비스의 클라이언트) 중 우리에게 해당하는 것은 없다. 사실상 **Sign in with Apple 을 iOS 앱에 넣어야 한다**. 스키마는 이미 대비돼 있다 (D-34, `AuthProvider.APPLE`).

딸린 의무
- 애플 로그인 계정 탈퇴 시 Apple REST API 로 토큰 폐기(revoke) 를 해야 한다. D-24 의 카카오 unlink 와 같은 자리에 넣는다
- 앱 안 회원 탈퇴는 이미 있다 (심사 5.1.1(v) 충족)

### 4.3 카카오 로그인 — 웹뷰 안에서 그대로 쓰면 안 된다
- 지금의 웹 로그인(`/auth/kakao` → `kauth.kakao.com`) 을 앱 웹뷰에서 그대로 열면 카카오톡 앱 호출(커스텀 스킴, Android `intent:`) 이 웹뷰에서 실패한다. 카카오 문서도 "웹뷰에서는 앱을 실행하지 못하고 에러가 발생" 한다고 하고, 우회하려면 스킴 가로채기 코드를 셸에 넣어야 한다. 결국 사용자는 웹뷰 안에서 카카오 ID/비밀번호를 치게 된다 → A1 실패
- 권장: **카카오 네이티브 SDK 로 로그인** (iOS `loginWithKakaoTalk`, Android 동일. 카카오톡이 없으면 `loginWithKakaoAccount` 로 폴백, 이 경우도 웹뷰가 아니라 시스템 브라우저 사용). SDK 가 받은 카카오 액세스 토큰을 우리 API 에 보내 자체 JWT 로 바꾼다 (7장)
- API 는 받은 토큰을 `GET kapi.kakao.com/v1/user/access_token_info` 로 확인하고 **응답의 `app_id` 가 우리 앱 ID 인지 검사** 해야 한다 (다른 앱에서 받은 토큰 재사용 차단). 이후 `/v2/user/me` 로 사용자 조회는 지금 코드 그대로
- 카카오 개발자센터 등록(사용자 작업): 네이티브 앱 키 사용, 플랫폼에 iOS 번들 ID, Android 패키지명과 **키 해시 3개**(디버그, 업로드 키, Google Play 앱 서명 키). Play 배포본은 Google 이 다시 서명하므로 Play Console 의 앱 서명 키 SHA-1 을 Base64 로 바꾼 값이 빠지면 스토어 설치본만 KOE009 로 실패한다
- 리다이렉트: Android 는 `kakao{네이티브앱키}://oauth` 스킴 액티비티, iOS 는 URL 스킴 `kakao{네이티브앱키}` 와 `LSApplicationQueriesSchemes`(`kakaokompassauth`, `kakaolink`). Expo 에서는 config plugin 으로 들어간다

### 4.4 Google Play
- 웹뷰만 감싼 앱은 스팸/최소 기능 정책으로 제거 대상이라고 Google 이 밝혀 왔다. 4.1 과 같은 대응으로 충분
- **신규 개인 개발자 계정(2023-11-13 이후 생성)은 프로덕션 출시 전에 테스터 12명 이상이 14일 연속 참여한 비공개 테스트가 필수** 다. 일정의 최장 경로가 이것이다. 조직 계정은 면제지만 D-U-N-S 번호가 필요하다

### 4.5 쿠키와 세션 유지
- WKWebView(iOS) 와 Android WebView 모두 기본 저장소를 쓰면 httpOnly 쿠키가 앱 재시작 후에도 남는다. 현재 `wwm_session`(30일) 구조를 그대로 쓴다. Android 는 백그라운드 진입 시 `CookieManager.flush()` 를 호출해 강제 종료에도 유지되게 한다
- 쿠키가 웹 도메인에만 있으므로 웹뷰는 `whenwemeet.day` 만 띄우고, 그 밖의 도메인(카카오 CDN 제외) 은 외부 브라우저로 연다
- 30일 만료 후 웹이 `/login` 을 보여주면, 앱 안에서는 그 화면의 카카오 버튼이 네이티브 로그인을 부르도록 분기해야 한다 (7장)

### 4.6 푸시 (이번 범위 아님)
나중에 넣을 때: Expo Notifications(APNs 와 FCM 을 한 API 로), API 에 기기 토큰 테이블과 발송 작업, iOS 권한 요청 화면. 셸을 Expo 로 두면 웹 재작성 없이 추가 가능하다. 지금 하지 않는 이유는 MVP 기획 4장 그대로.

### 4.7 아이콘과 스플래시
`brand/app-icon.svg`(512 원본) 에서 생성. iOS 는 1024×1024 불투명 PNG 1장(투명 배경 불가), Android 는 적응형 아이콘(전경 `logo-symbol.svg` + 배경색) 와 Play 스토어용 512 PNG. 스플래시는 심볼 + 배경색(라이트 `#F4F3F1`, 다크 `#121214`, `layout.tsx` 의 themeColor 와 동일). 크기 변환은 Expo 가 빌드 때 한다.

## 5. 현재 웹의 앱 준비 상태

| 항목 | 상태 | 필요한 조치 |
|------|------|------------|
| Web App Manifest | **없음** (`app/manifest.ts`, `public/*.webmanifest` 없음) | `name`, `short_name`, `display: standalone`, `start_url: /`, `theme_color`, `background_color`, 아이콘 |
| 아이콘 | 192, 512, apple-touch 180 있음 | maskable 512 추가 (가장자리 여백), 스토어용 1024 |
| iOS 홈 화면 메타 | 없음 | `metadata.appleWebApp` (`capable`, `title`, `statusBarStyle`) |
| safe-area | **됨** (`viewportFit: cover`, 화면마다 `env(safe-area-inset-*)`) | 없음 |
| 테마 색 | 됨 (라이트/다크 `themeColor`) | 없음 |
| 서비스 워커, 오프라인 화면 | 없음 | PWA 설치 조건으로는 불필요. 앱은 셸이 오프라인 화면을 그린다 |
| 공유 | `navigator.share` 후 클립보드 폴백 (`SettingsScreen`) | Android WebView 는 Web Share 를 지원하지 않아 복사로 떨어진다 → 앱에서는 브리지로 네이티브 공유 |

| 외부 리소스 | Pretendard 를 jsDelivr 에서 로드 | 앱도 그대로 동작. 첫 실행 오프라인이면 기본 글꼴로 보인다 (허용) |

## 6. 네이티브로 더할 것 (4.2 대응이자 앱을 쓰는 이유)

| 기능 | 필수/선택 | 비고 |

| 네이티브 로그인 화면 (카카오톡 앱 로그인 + 애플 로그인) | 필수 | A1. 4.8 충족. 웹뷰가 아닌 화면 |

## 7. 추천: ⑤ Expo 셸 + WebView

**이유**: 웹을 고치지 않고(정적 내보내기 불가 문제를 피함) iOS 와 Android 를 한 코드로 내고, 4.2 와 4.8 이 요구하는 네이티브 부분(로그인, 링크, 공유, 오프라인)만 네이티브로 둔다. 웹 배포가 곧 앱 화면 업데이트다. 푸시와 위젯도 나중에 같은 셸에 붙는다.

### 7.1 로그인 흐름 (앱)

```
앱 로그인 화면
  ├ 카카오: 카카오 SDK → 카카오 액세스 토큰 ─► POST /v1/auth/kakao/native { accessToken }
  │                                              API: access_token_info 로 app_id 검사 → /v2/user/me → upsert (지금 콜백과 같은 서비스 함수)
  ├ 애플(iOS): expo-apple-authentication → identityToken ─► POST /v1/auth/apple/native { identityToken, nickname? }
  │                                              API: Apple 공개키(JWKS)로 서명, iss, aud(번들 ID), exp 검증 → upsert
  └ 애플(Android): 시스템 브라우저로 웹 방식 애플 로그인(Service ID) → 앱 링크로 셸 복귀 (세부는 P1 설계)
API 응답: { handoff } (60초 유효, 1회용 교환 토큰. 세션 JWT 아님)
앱: 웹뷰로 https://whenwemeet.day/auth/app?h=<handoff>&next=/ 를 연다
웹 route handler: POST /v1/auth/handoff 로 세션 JWT 교환 → wwm_session httpOnly 쿠키 → next 로 302
```

- 쿠키 방식을 유지한다 (Bearer 를 앱에 저장하지 않음). 웹 코드의 프록시, `proxy.ts`, 401 처리 전부 그대로
- 세션 JWT 대신 handoff 를 URL 에 싣는 이유: 지금의 `/auth/callback?token=` 은 30일짜리 JWT 가 URL 에 실린다(D-10). 앱에서는 이 URL 을 우리가 직접 만들므로 수명을 60초로 줄일 수 있다
- 웹은 셸의 User-Agent 접미사(예: `WhenwemeetApp/1.0`)로 앱 안인지 안다. 앱 안의 `/login` 카카오 버튼과 로그아웃, 탈퇴 완료는 `window.ReactNativeWebView.postMessage` 로 셸에 알린다 (셸이 네이티브 로그인 화면으로 돌아감)
- 애플 로그인은 첫 로그인에만 이름을 준다. 닉네임이 없으면 "새 사용자" 로 만들고 D-36 대로 사용자가 바꾼다. 이메일은 받지 않는다 (MVP 수집 최소화 유지)
