# 푸시 알림 설계

- 이슈: #188 (기획 `docs/기획/푸시-알림.md`, 2026-11-10 승인)
- 상태: 설계 승인 (2026-11-11, 팀원 변경 2분 묶음과 무응답 미재전송 확인) (GATE 2). 스키마는 GATE 3 대상
- 결정기록: D-80 ~ D-99, (#277 주간 요약과 조용한 팀 깨우기) D-203 ~ D-205, (#528 공지 푸시) D-287
- 공통 규칙(응답 봉투 `{ status, data, message, error? }`, Int ID, 멤버 검사, 날짜 ISO UTC)은 `api.md` 1장 그대로. 이 문서의 `{ data: ... }` 는 `data` 필드의 모양
- 회차 계산은 `apps/api/src/events/recurrence.ts` 의 `expand()` 를 그대로 쓴다 (반복-일정.md 3장). 이 문서는 펼치기 규칙을 바꾸지 않는다

## 1. 한눈에

```
[셸 (Expo 1.1)]                [웹 (웹뷰 안)]                         [API (Railway api 1대)]                 [Expo 푸시]
 expo-notifications
   권한, Expo 토큰  ◄─ pushRequest/pushStatus ─┐
   ─ wwm:app 이벤트(토큰, 권한) ─────────────► │ PUT /api/me/push-devices ──► PushDevice upsert
                                              │
 일정 저장, 기념일, 합류, 변경 ───────────────────────────────────────► PushNotification (예약)
                                                                       30초 틱 (DB 임대 1개만)
                                                                        ├ 일정 알림, 기념일 계산 → 예약
                                                                        ├ 예약 시각 도래 → 받을 기기 펼치기 → PushDelivery
                                                                        └ 100개씩 POST /push/send ───────────► APNs / FCM
                                                                          15분 뒤 영수증 확인 ◄── getReceipts
 알림 누름 → data.url 경로를 웹뷰로 연다
```

- 셸은 세션을 갖지 않는다(D-44). 그래서 **토큰 등록은 웹이 자기 세션으로 한다** (D-80)
- 발송 예약은 API 프로세스 안의 30초 틱이 한다. Railway 서비스를 늘리지 않는다 (D-87)
- 같은 알림이 한 기기에 두 번 가지 않는 것은 DB 유일 키 두 개가 보장한다. 임대(lease)는 효율용 (D-89)

## 2. 기기 등록

### 2-1 앱 판정과 푸시 지원 (D-81)

| 판정 | 규칙 (`apps/web/src/lib/app-bridge.ts`) |
|------|------|
| `isInApp()` | 지금 그대로 (UA `WhenwemeetApp/<버전> (<os>)` + `window.ReactNativeWebView`) |
| `appSupportsPush()` | `isInApp()` 이고 UA 버전이 `1.1.0` 이상 (숫자 세 칸 비교, 형식이 틀리면 false) |

- 1.0.x 앱은 새 메시지를 모르므로(목록에 없는 type 은 버린다, D-53) 웹은 보내지 않고 웹 브라우저와 같은 화면을 그린다. 이전 앱 버전은 지금처럼 동작한다 (기획 6장)

### 2-2 브리지 메시지 추가 (D-53 확장, 모두 `v: 1`)

웹 → 셸 (`postToApp`, `appSupportsPush()` 일 때만):

| type | 필드 | 셸 동작 |
|------|------|--------|
| `pushStatus` | `id: string(1~40)` | 권한 상태를 읽고 허용이면 Expo 토큰을 구해 `pushStatus` 응답 |
| `pushRequest` | `id: string(1~40)` | Android 채널 생성 → `canAskAgain` 이면 OS 권한 창 → 결과로 `pushStatus` 응답. 이미 거부되어 다시 물을 수 없으면 창 없이 응답 |
| `openSettings` | - | `Linking.openSettings()` (OS 앱 설정) |

셸 → 웹 (응답, 새로 둔다): `webview.injectJavaScript` 로 `window.dispatchEvent(new CustomEvent('wwm:app', { detail }))` 를 실행한다. 웹뷰 현재 주소가 `WEB_ORIGIN` 일 때만.

```ts
detail = { v: 1, type: 'pushStatus', id,                 // 요청의 id 그대로
           permission: 'granted' | 'denied' | 'undetermined',
           canAskAgain: boolean,
           token: string | null,                          // granted 이고 토큰을 얻었을 때만 'ExponentPushToken[...]'
           platform: 'IOS' | 'ANDROID', appVersion: '1.1.0' }
```

- 웹은 `lib/app-bridge.ts` 에 `requestPushStatus(kind: 'status' | 'request'): Promise<PushStatus | null>` 하나를 둔다. id 로 응답을 짝짓고 5초(권한 창은 60초) 안에 없으면 null
- Expo 토큰은 `getExpoPushTokenAsync({ projectId: extra.eas.projectId })`. 실패(에뮬레이터, 네트워크)면 `token: null`
- 셸이 토큰을 API 에 직접 보내지 않는 이유: 셸에는 세션이 없고(D-44), 웹뷰 쿠키는 `whenwemeet.day` httpOnly 라 셸 fetch 에 실린다는 보장이 없다. 웹은 쿠키 → `/api/*` 프록시로 이미 인증된다 (D-80)

### 2-3 흐름

| 때 | 웹 동작 |
|----|--------|
| 로그인된 화면이 처음 그려질 때, 앱이 다시 앞으로 올 때(`visibilitychange` → visible) | `appSupportsPush()` 면 `pushStatus`. 토큰이 있으면 `PUT /api/me/push-devices` (같은 토큰은 1시간에 한 번만, `sessionStorage` 기록). 토큰이 없거나 권한이 granted 가 아닌데 `localStorage.wwm_push_token` 이 있으면 `DELETE /api/me/push-devices` 후 그 값을 지운다 (OS 에서 알림을 끈 기기 정리) |
| 권한 시트 [알림 받기] | `pushRequest` → granted 면 위와 같이 등록 |
| 등록 성공 | `localStorage.wwm_push_token = token` |
| 로그아웃 | 로그아웃 폼에 `pushToken`(= `localStorage.wwm_push_token`) 숨은 필드. `/auth/logout` route handler 가 쿠키를 지우기 전에 `DELETE ${API_URL}/v1/me/push-devices { token }` (Bearer = 그 쿠키, 2초 제한, 실패해도 로그아웃은 진행). 이후 `localStorage.wwm_push_token` 삭제 (D-83) |
| 탈퇴 | `DELETE /me` 의 User Cascade 로 기기 행 삭제. 웹은 `wwm_push_token` 삭제 |
| 다른 계정으로 로그인 | 같은 토큰으로 `PUT` → 행의 `userId` 를 새 사용자로 바꾼다 (한 기기는 한 사용자) |
| 발송 응답 `DeviceNotRegistered` (앱 삭제 등) | API 가 그 토큰 행 삭제 (5-7) |

- 세션 만료(30일)는 로그아웃으로 보지 않는다. 같은 사용자라 알림은 계속 가고, 누르면 로그인 후 그 화면으로 간다 (D-83)
- 한 사용자 기기는 최대 10대. 넘으면 `lastSeenAt` 가 가장 오래된 기기를 지운다

## 3. 스키마 초안 (GATE 3)

`docs/설계/schema.prisma` 는 다른 작업(#187 후속)이 고치는 중이라 이 문서에만 둔다. 구현 때 `apps/api/prisma/schema.prisma` 에 그대로 옮긴다.

```prisma
/// (#188) 일정 알림 시각. 시간 일정은 AT_START ~ DAY_1, 종일 일정은 DAY_OF_0900, DAY_BEFORE_0900 (4장)
enum EventReminder {
  NONE
  AT_START
  MIN_10
  HOUR_1
  DAY_1
  DAY_OF_0900
  DAY_BEFORE_0900
}

/// (#188) 기기 OS
enum DevicePlatform {
  IOS
  ANDROID
}

/// (#188) 알림 종류. 내 정보 > 알림 의 토글 4개와 1:1
enum PushKind {
  REMINDER
  CHANGE
  ANNIVERSARY
  JOIN
}

/// (#188) PENDING 예약 → DISPATCHED 받을 기기로 펼침 / CANCELLED 묶음으로 취소 / SKIPPED 10분 넘게 늦어 버림
enum PushNotificationStatus {
  PENDING
  DISPATCHED
  CANCELLED
  SKIPPED
}

/// (#188) QUEUED → SENDING → SENT(Expo 접수) / FAILED
enum PushDeliveryStatus {
  QUEUED
  SENDING
  SENT
  FAILED
}

model User {
  // ... 기존 필드 그대로
  /// (#188) 내 정보 > 알림 → (#369) NotificationPreference 행으로 옮김 (D-249, 아래)
  notificationPreferences NotificationPreference[]
  /// (#188) 마지막 앱 로그인 (handoff 교환 성공). 권한 허용률 지표의 분모 (10-3)
  lastAppLoginAt    DateTime?

  pushDevices    PushDevice[]
  pushDeliveries PushDelivery[]
}

/// (#369, D-249) 사용자 알림 종류 설정. 행이 없으면 코드 기본값 표(notification-preferences.ts)
/// 기본 켬: REMINDER CHANGE ANNIVERSARY JOIN WEEKLY POLL NOTICE, 기본 끔: WEEKLY_NUDGE (D-204). (#528) NOTICE 는 공지 (D-287)
enum NotificationPreferenceKind { REMINDER CHANGE ANNIVERSARY JOIN WEEKLY WEEKLY_NUDGE POLL NOTICE }

model NotificationPreference {
  userId    Int
  kind      NotificationPreferenceKind
  enabled   Boolean
  updatedAt DateTime @updatedAt
  user User @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@id([userId, kind])
}

model Membership {
  // ... 기존 필드 그대로
  /// (#188) 팀 설정 "이 팀 알림 받기". 기본 켬
  notify Boolean @default(true)
}

model Event {
  // ... 기존 필드 그대로
  /// (#188) 알림 시각. 기본 없음
  reminder      EventReminder @default(NONE)
  /// (#188) 한 번짜리 일정의 알림 시각(UTC). 반복 원본이거나 NONE 이면 null. 저장할 때 계산 (4-2)
  remindAt      DateTime?
  /// (#188) 알림 시각을 정하는 값(시작, 끝, 종일, 알림, 반복, 반복 종료일)을 마지막으로 바꾼 시각 (4-3)
  reminderSetAt DateTime      @default(now())

  @@index([remindAt])
  @@index([reminder, repeat])
}

model EventException {
  // ... 기존 필드 그대로
  /// (#188) 이 회차의 알림. null 이면 원본 값
  reminder      EventReminder?
  /// (#188) 이 회차의 시각이나 알림을 바꾼 시각. null 이면 원본 값
  reminderSetAt DateTime?
}

/// (#188) 푸시를 받을 기기. 로그아웃하면 지우고, 탈퇴하면 Cascade 로 지운다
model PushDevice {
  id         Int            @id @default(autoincrement())
  userId     Int
  /// Expo 푸시 토큰 'ExponentPushToken[...]'. 한 기기는 한 사용자
  token      String         @unique @db.VarChar(200)
  platform   DevicePlatform
  /// 등록한 앱 버전 (문제 추적용)
  appVersion String         @db.VarChar(20)
  createdAt  DateTime       @default(now())
  /// 웹이 마지막으로 등록을 확인한 시각 (1시간 단위)
  lastSeenAt DateTime       @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, lastSeenAt])
}

/// (#188) 보낼 알림 한 건 (사람, 기기와 무관한 "무엇을 언제"). dedupeKey 로 한 번만 생긴다
model PushNotification {
  id            Int                    @id @default(autoincrement())
  kind          PushKind
  /// 중복 방지 키 (5-2). 같은 키는 다시 만들지 않는다
  dedupeKey     String                 @unique @db.VarChar(120)
  groupId       Int
  scheduledAt   DateTime
  status        PushNotificationStatus @default(PENDING)
  /// CHANGE 묶음 키 "{actorId}:{eventId}" (5-4). 그 밖은 null
  coalesceKey   String?                @db.VarChar(40)
  /// CHANGE 에 보일 동작 (묶은 결과). 그 밖은 null
  changeAction  EventLogAction?
  /// 대상. FK 를 걸지 않는다 (원본이 지워져도 기록은 남고, 발송 때 판정)
  eventId       Int?
  occurrence    DateTime?              @db.Date
  eventLogId    Int?
  anniversaryId Int?
  /// CHANGE 의 변경한 사람, JOIN 의 합류한 사람. 받는 사람에서 뺀다
  actorId       Int?
  /// 펼칠 때 만든 문구와 경로 { title, subtitle, body, url, expiration }. 기록과 재현용
  payload       Json?
  dispatchedAt  DateTime?
  createdAt     DateTime               @default(now())

  group      Group          @relation(fields: [groupId], references: [id], onDelete: Cascade)
  deliveries PushDelivery[]

  @@index([status, scheduledAt])
  @@index([coalesceKey, status])
  @@index([createdAt])
}

/// (#188) 기기 하나에 보낸 기록. (알림, 토큰) 이 유일해 한 기기에 한 번만 간다
model PushDelivery {
  id               Int                @id @default(autoincrement())
  notificationId   Int
  userId           Int
  token            String             @db.VarChar(200)
  platform         DevicePlatform
  status           PushDeliveryStatus @default(QUEUED)
  attempts         Int                @default(0)
  /// Expo 티켓 id (SENT 일 때)
  ticketId         String?            @db.VarChar(64)
  /// Expo 오류 코드 (DeviceNotRegistered 등) 또는 TIMEOUT, EXPIRED
  error            String?            @db.VarChar(64)
  /// 영수증 결과 'ok' | 오류 코드. null 이면 아직 확인 안 함
  receipt          String?            @db.VarChar(64)
  sentAt           DateTime?
  receiptCheckedAt DateTime?
  createdAt        DateTime           @default(now())

  notification PushNotification @relation(fields: [notificationId], references: [id], onDelete: Cascade)
  user         User             @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([notificationId, token])
  @@index([status, createdAt])
  @@index([status, receiptCheckedAt, sentAt])
}

/// (#188) 프로세스 안 예약 작업의 임대와 진행 위치. 행 1개('push')
model SchedulerLease {
  name        String    @id @db.VarChar(40)
  /// 임대를 가진 프로세스 id (기동 때 랜덤)
  holder      String?   @db.VarChar(40)
  leaseUntil  DateTime
  /// 일정 알림과 기념일 계산을 마친 시각 (5-1 창의 아래 끝)
  cursor      DateTime?
  /// 하루 한 번 청소를 마친 KST 날짜
  dailyDoneOn DateTime? @db.Date
  updatedAt   DateTime  @updatedAt
}
```

`Group` 에 `pushNotifications PushNotification[]` 관계 필드를 더한다.

**마이그레이션** (`<시각>_push_notifications`, 추가형만, 배포.md 정책):
1. enum 5개, 테이블 4개 생성
2. 컬럼 추가: User 5개, Membership 1개, Event 3개, EventException 2개. 모두 기본값 또는 nullable 이라 기존 행은 알림 없음, 설정 모두 켬
3. 인덱스 추가 3개 (`Event.remindAt`, `Event.(reminder, repeat)`, 위 테이블 인덱스)
4. `INSERT INTO SchedulerLease (name, leaseUntil, updatedAt) VALUES ('push', '1970-01-01', NOW(3))`
- 되돌릴 때는 이전 이미지로 롤백만 하면 된다 (새 컬럼은 기본값이 있어 옛 코드가 무시). DROP 은 하지 않는다

## 4. 일정 알림 시각

### 4-1 선택지와 검증 (D-84)

| 값 | 화면 | 쓸 수 있는 일정 | 알림 시각 (회차 시작 `s` 기준) |
|----|------|----------------|------|
| `NONE` | 없음 | 모두 | - |
| `AT_START` | 정시 | 시간 일정 | `s` |
| `MIN_10` | 10분 전 | 시간 일정 | `s - 10분` |
| `HOUR_1` | 1시간 전 | 시간 일정 | `s - 1시간` |
| `DAY_1` | 1일 전 | 시간 일정 | `s - 24시간` |
| `DAY_OF_0900` | 당일 오전 9시 | 종일 일정 | `s` 의 KST 날짜 09:00 (= `s + 9시간`) |
| `DAY_BEFORE_0900` | 전날 오전 9시 | 종일 일정 | `s` 의 KST 전날 09:00 (= `s - 15시간`) |

- 순수 함수 `apps/api/src/push/remind-at.ts`: `remindAt(startsAt, allDay, reminder): Date | null`. 종일은 `startsAt` 의 KST 날짜로 계산 (startsAt 이 KST 자정이 아니어도 같은 날짜 규칙)
- 생성: `reminder` 생략은 `NONE`. 종일 여부와 맞지 않는 값이면 400 VALIDATION_FAILED (`details[0].field = 'reminder'`, message "종일 일정에는 고를 수 없는 알림이에요" / "시간 일정에는 고를 수 없는 알림이에요")
- 수정: 합친 결과로 검사. 본문에 `reminder` 가 없는데 `allDay` 가 바뀌어 지금 값이 맞지 않게 되면 `NONE` 으로 바꾼다 (웹도 종일 전환 시 "없음" 으로 되돌린다)
- "이 일정만"(PATCH this): `EventException.reminder` 에 저장. 원래 회차 값(원본 reminder)과 같으면 null. 반복 원본의 다른 필드처럼 "바꾼 필드만" 규칙(D-65)을 따른다
- 같은 값이면 저장하지 않는 규칙(#62)에 `reminder` 도 포함

### 4-2 저장 값 (D-85)

| 일정 | `remindAt` | 계산 시점 |
|------|-----------|----------|
| 한 번짜리 | `remindAt(startsAt, allDay, reminder)` | 생성, 그리고 시작/끝/종일/알림/반복이 바뀌는 모든 수정 |
| 반복 원본 | null (회차마다 틱에서 계산, 5-3) | - |

한 번짜리를 반복으로 바꾸면 `remindAt = null`, 반복을 끄면 다시 계산.

### 4-3 "지난 시각으로 저장하면 안 보냄" (D-86)

알림을 정하는 값을 바꾼 시각 `reminderSetAt` 를 둔다.
- `Event.reminderSetAt = now`: 생성, 그리고 `startsAt`, `endsAt`, `allDay`, `reminder`, `repeat`, `repeatUntil` 중 하나라도 바뀐 수정 ("이후 모두" 로 새 원본을 만들면 새 원본에 now)
- `EventException.reminderSetAt = now`: 그 회차의 시각, 종일, 알림이 바뀐 "이 일정만" 수정
- 회차의 기준 = `max(Event.reminderSetAt, EventException.reminderSetAt ?? 0)`
- **알림 시각 < 기준 이면 보내지 않는다.** 예: 30분 뒤 일정에 1시간 전 → 알림 시각이 저장보다 앞 → 없음. 18:00 일정을 17:30 에 19:00 으로 옮김 → 새 알림 18:00 은 기준 뒤 → 보냄
- 제목, 메모만 바꾸면 기준이 그대로라 이미 잡힌 알림에 영향이 없다

### 4-4 다시 보내는 경우
알림 키(5-2)에 알림 시각이 들어 있다. 시각이나 선택을 바꿔 **알림 시각이 달라지면 새 키라 다시 보낸다.** 같은 시각이면 같은 키라 다시 보내지 않는다 (기획 3-2).

### 5-2 중복 방지 키 (D-89)

| 종류 | dedupeKey | 뜻 |
|------|-----------|----|
| REMINDER | `R:{eventId}:{occurrence YYYY-MM-DD 또는 -}:{알림 시각 epoch 초}` | 일정, 회차, 알림 시각 |
| ANNIVERSARY | 당일 `A:{anniversaryId}:{그날 KST 날짜}`, 하루 전 `…:D1`, 일주일 전 `…:D7` (#269, D-146) | 기념일 하나, 그날, 시점마다 1건. 당일 키는 #269 전과 같다 |
| CHANGE | `C:{묶음의 첫 EventLog id}` | 묶음 하나 |
| JOIN | `J:{membershipId}` | 합류 한 번 |
| WEEKLY (#277) | `W:{groupId}:{그 주 월요일 YYYY-MM-DD}` | 팀 하나, 주 하나 (변형과 무관) |
| POLL (#189) | 열림 `PO:{pollId}`, 정함 `PC:{pollId}`, 마감 `PD:{pollId}` | 투표 하나, 단계마다 1건 (D-241) |
| NOTICE (#528) | `N:{noticeId}` | 공지 하나에 1건 (D-287) |

- `PushNotification.dedupeKey` 유일 → 같은 알림은 한 번만 생긴다 (재시작, 틱 두 번, 프로세스 둘)
- `PushDelivery (notificationId, token)` 유일 → 한 기기에 한 번만. 펼치기는 `updateMany where id, status=PENDING → DISPATCHED` 가 1행일 때만 해서 두 번 펼치지 않는다
- 발송은 **최대 한 번**: Expo 에 보내기 직전에 SENDING 으로 바꾸고, 응답을 못 받은 실패(타임아웃)는 다시 보내지 않는다 (5-6)

### 5-3 일정 알림 계산 (`ReminderPlanner`, 창 (lo, hi])

**한 번짜리**: `Event where remindAt > lo AND remindAt <= hi AND repeat IS NULL` (인덱스 `remindAt`). `remindAt >= reminderSetAt` 인 것만.

**반복**: 후보 원본 =
- `reminder != NONE AND repeat IS NOT NULL` 이고 `seriesCandidateWindow(lo - 9시간, hi + 24시간)` 조건 (반복-일정.md 4-2), 그리고
- `EventException where reminder IS NOT NULL AND reminder != NONE AND occurrence BETWEEN KST(lo) - 32일 AND KST(hi) + 32일` 의 eventId (원본은 NONE 이지만 회차만 알림을 고른 경우)

후보마다 예외를 읽어 `expand(series, exceptions, lo - 9시간, hi + 24시간)` → 회차마다
```
reminder = exception?.reminder ?? series.reminder        (NONE 이면 건너뜀)
at = remindAt(회차.startsAt, 회차.allDay, reminder)     (종일 여부와 안 맞으면 건너뜀, 4-1)
lo < at <= hi 이고 at >= max(series.reminderSetAt, exception?.reminderSetAt) 이면 예약
```
- 창의 앞뒤 여유: 알림 시각은 회차 시작의 -24시간 ~ +9시간 사이라 회차 시작이 `[lo - 9시간, hi + 24시간]` 에 있어야 한다
- 예약 행: `kind REMINDER, scheduledAt = at, eventId, occurrence(반복만), payload` (문구는 이때 만든다, 6장). 바로 5-6 에서 펼친다
- 비용: 30초마다 알림 켠 반복 원본 수만큼 펼친다. 원본 1개당 회차 최대 몇 개라 수천 개까지 문제없다. 그 이상이면 원본에 다음 알림 시각 캐시를 두는 것으로 바꾼다 (위험 R2)

### 5-4 팀원 변경 묶기 (`ChangeCoalescer`, D-90)

EventLog 를 쓰는 **같은 트랜잭션** 안에서 (EventsRepository 의 `...WithLogTx` 들):

```
key = "{actorId}:{log.eventId}"     (actorId 가 null 이거나 PERSONAL 팀이면 아무것도 하지 않음)
p = PushNotification where coalesceKey = key AND status = PENDING  FOR UPDATE
p 없음 → 생성 { kind CHANGE, dedupeKey "C:{log.id}", scheduledAt = now + 2분, coalesceKey key,
                changeAction = log.action, eventLogId = log.id, eventId = log.eventId, actorId }
p 있음 → 아래 표. scheduledAt 은 그대로 (첫 변경부터 2분 고정 창)
```

| p.changeAction | 새 로그 | 결과 |
|---|---|---|
| CREATED | UPDATED | CREATED 유지, `eventLogId` = 새 로그 (최신 제목, 시각으로 "추가했어요") |
| CREATED | DELETED, 원본 행이 지워짐 (한 번짜리 삭제, "이후 모두" 첫 회차 삭제) | `status = CANCELLED` (둘 다 안 보냄) |
| CREATED | DELETED, 원본이 남음 ("이 일정만" 삭제, 뒤 회차부터 삭제) | CREATED 유지, `eventLogId` 그대로 |
| UPDATED | UPDATED | `eventLogId` = 새 로그 |
| UPDATED | DELETED | `changeAction = DELETED`, `eventLogId` = 새 로그 |

- "원본 행이 지워짐" 은 서비스가 이미 아는 값이라 `removesEvent: boolean` 으로 넘긴다
- "이후 모두" 를 뒤 회차에서 하면 새 원본이 생겨 `log.eventId` 가 달라지므로 다른 묶음이다
- 반복 일정 동작 하나는 로그 1건이라 알림도 1건 (기획 3-3)
- **지연**: 변경 알림은 첫 변경 뒤 2분에 간다. 기획 P2 의 "수 초 안에" 는 3-3 의 묶기 규칙(2분 안 여러 번 수정은 마지막 1건, 추가 후 2분 안 삭제는 0건)과 같이 지킬 수 없어 3-3 을 따른다 (D-90)

**새 멤버 합류** (`GroupsService.join`, 새 멤버십이 생겼을 때만. 이미 멤버면 없음): 같은 트랜잭션에서 `{ kind JOIN, dedupeKey "J:{membershipId}", scheduledAt = now, actorId = 합류자 }`. 커밋 뒤 `PushScheduler.kick()` 으로 틱을 바로 한 번 돌린다(임대 규칙 그대로) (D-91).

### 5-5 기념일 (`AnniversaryPlanner`, D-92)

- 창 (lo, hi] 안에 KST 09:00 (`날짜 D 00:00 UTC`) 이 있으면 날짜 D 를 처리한다 (창은 10분 이하라 많아야 하루)
- 모든 Anniversary 를 읽어 `anniversaryItemsOn(a, D)` 로 그날 항목을 구한다. 웹 `lib/anniversary.ts` 의 `occurrencesInRange(a, D, D)` 를 서버로 옮긴 순수 함수 `apps/api/src/push/anniversary-items.ts` (D-59, D-60, D-62 규칙 그대로). 테스트는 기획 `기념일-자동표시.md` 3-5 예시표를 그대로 쓴다
- 항목이 있으면 기념일 하나에 1건. 항목이 둘이면 우선순위(N주년 > N일 > 매년/원래 날짜) 첫 항목으로 문구를 만든다
- `Anniversary.updatedAt > D 09:00` 이면 건너뛴다 (9시 넘어 등록, 수정한 오늘 기념일은 보내지 않음. 4-3 과 같은 원칙)
- 예약 행: `kind ANNIVERSARY, scheduledAt = D 09:00, anniversaryId, payload`

**알림 시점 (#269, D-144 ~ D-147)**. `AnniversaryReminder(anniversaryId, offset)` 행(#369, 켜진 시점마다 하나, `offset` = `DAY_OF | DAY_BEFORE | WEEK_BEFORE`, D-249)의 시점 `o`(0, 1, 7일) 마다:
```
그날 T = D + o일
items = anniversaryItemsOn(a, T)
o = 7 이면 items 에서 DAYS(100일 단위) 를 뺀다   (일주일 전은 N주년, 매년, 원래 날짜만)
items 가 비면 건너뜀, 아니면 첫 항목으로 문구 (6장), scheduledAt = D 09:00
```
- 보내는 날 D 의 09:00 기준으로 `updatedAt` 을 본다 (위 규칙 그대로). 알림 시각이 지난 뒤 설정을 바꾼 회차는 보내지 않는다
- 셋 다 꺼진 기념일(알림 없음)은 계산하지 않는다

| 항목 \ 시점 | 당일 | 하루 전 | 일주일 전 |
|------|------|--------|----------|
| ORIGINAL (등록한 그날) | O | O | O |
| DAYS (100일 단위) | O | O | X |
| YEARS (N주년) | O | O | O |
| YEARLY (매년) | O | O | O |

**멤버 생일 (#305, D-232)**. 같은 틱에서 `planBirthdays`: 생일(`User.birthday` 'MM-DD')이 있고 시점이 하나라도 켜진 사람의, 생일을 보이는(`Membership.showBirthday`) TEAM 팀 멤버십마다 위 시점 표의 YEARLY 줄 그대로(2월 29일은 평년 2월 28일). 시점은 생일인 사람이 고른다(`BirthdayReminder(userId, offset)` 행, 기념일과 같은 `ReminderOffset`, 가입 때 당일 행 하나 = 기본 당일만, #369 D-249). 문구는 이름 "{팀 표시 이름 ?? 닉네임} 생일", 라벨 없음. 예약 행 `kind ANNIVERSARY, dedupeKey B:{userId}:{groupId}:{그날}{:D1|:D7}, actorId = 생일인 사람, anniversaryId null`. 펼칠 때 actorId 를 받는 사람에서 빼고, 그 사람이 아직 그 팀에 생일을 보이며 생일이 그날인지 다시 본다(아니면 SKIPPED). `updatedAt` 규칙은 없다(생일 칸에 개정 시각이 없고, 9시 창을 지난 변경은 다음 해까지 예약되지 않는다)

### 5-6 펼치기와 발송 (`PushDispatcher`)

```
A. 예약: PushNotification where status = PENDING AND scheduledAt <= now  (scheduledAt 순, 최대 500)
   scheduledAt < now - 10분  → SKIPPED (D-88)
   그 밖 → 트랜잭션: updateMany(id, PENDING → DISPATCHED, dispatchedAt) 가 1행일 때만
           받는 사람 × 기기를 PushDelivery createMany skipDuplicates (QUEUED)
           CHANGE 는 이때 EventLog 를 읽어 문구를 만들고 payload 저장
B. 발송: PushDelivery where status = QUEUED (최대 1000)
   updateMany(ids, QUEUED → SENDING, attempts + 1) 후 100개씩 ExpoPushClient.send
```

**받는 사람** (한 쿼리: Membership ⋈ User ⋈ PushDevice, `groupId = n.groupId`):

| 종류 | 사람 | 설정 |
|------|------|------|
| REMINDER | (#248) 그 일정의 참여자 (모두면 팀원 모두, 등록자 여부와 무관). 참여자 없음이면 0명으로 DISPATCHED (D-138) | 설정 `REMINDER` AND `Membership.notify` |
| CHANGE | 팀원 중 `actorId` 아닌 사람 | `CHANGE AND notify` |
| ANNIVERSARY | 팀원 모두 | `ANNIVERSARY AND notify` |
| JOIN | 팀원 중 합류자 아닌 사람 | `JOIN AND notify` |
| WEEKLY SUMMARY (#277) | 팀원 모두 | `WEEKLY AND notify` |
| WEEKLY NUDGE (#277) | 팀원 모두 | `WEEKLY_NUDGE AND notify` (요약 토글과 별개, 기본 끔 D-204) |
| POLL 열림 (#189) | 투표 대상 중 연 사람 아닌 사람. 투표가 진행 중일 때만(취소, 정함이면 SKIPPED) | `POLL AND notify` |
| POLL 정함 (#189) | 투표 대상 중 정한 사람 아닌 사람, `joinedAt <= createdAt` | `POLL AND notify` |
| POLL 마감 (#189) | 연 사람 한 명. 진행 중일 때만 | `POLL AND notify` |
| NOTICE (#528) | 팀과 무관하게 기기가 있는 모든 사용자 (16장) | `NOTICE` (팀 설정 `notify` 는 보지 않는다) |

(#369) 설정 X 가 켜짐 = `NotificationPreference(userId, X)` 행의 `enabled`, 행이 없으면 기본값(기본 켬이면 "끈 행이 없음", 기본 끔이면 "켠 행이 있음" 으로 거른다, `preferenceOn`, D-249)

- 펼치는 순간의 팀원이다 (그 사이 나간 사람은 받지 않음). 기기가 없으면 PushDelivery 도 없다
- (#297, D-180) 지난 일을 알리는 CHANGE, JOIN 은 거기에 더해 `Membership.joinedAt <= PushNotification.createdAt` 인 팀원만. 들어오기 전 일은 알리지 않는다

  | 종류 | 합류 시각 조건 | 기준 시각 |
  |------|---------------|----------|
  | CHANGE (일정 변경 묶음) | `joinedAt <= createdAt` | 묶음을 연 첫 변경 시각. 묶음 중에 들어온 사람은 그 뒤 변경이 같은 묶음에 합쳐져도 받지 않는다 (알림 문구가 들어오기 전 변경까지 합친 결과일 수 있다). 들어온 뒤의 변경은 새 소식에 보인다 |
  | CHANGE (가져오기, `I:`) | `joinedAt <= createdAt` | 가져오기를 마친 시각 |
  | JOIN | `joinedAt <= createdAt` | 합류한 시각 (합류 트랜잭션에서 예약) |
  | REMINDER, ANNIVERSARY | 없음 | 앞날 알림. 펼칠 때 팀원이면 받는다 |
  | WEEKLY (#277) | 없음 | 이번 주 일정과 비는 시간을 알리는 앞날 알림. 예약 뒤(월요일 아침) 들어온 사람도 펼칠 때 팀원이면 받는다 |

  `EventLog.createdAt` 이 아니라 예약 시각을 쓰는 이유: 묶음의 `eventLogId` 는 마지막 변경으로 바뀌지만 문구는 묶음 전체를 합친 결과이고, 가져오기와 합류는 가리키는 로그가 없다. 예약 행은 세 경우 모두 그 일이 생긴 트랜잭션에서 만들어져 같은 기준이 된다
- 다시 들어온 사람: 나가면 멤버십 행을 지우고 다시 들어오면 새로 만든다 (`joinedAt` = 다시 들어온 시각). 나가 있던 동안과 그 전의 일은 새 소식, 알림 모두에서 빠진다
- 원본이 사라졌으면: REMINDER 는 `eventId` 일정이 없으면 SKIPPED (예약과 펼치기가 같은 틱이라 드묾), CHANGE 는 EventLog 스냅샷으로 보낸다

**Expo 요청** (D-94): `POST https://exp.host/--/api/v2/push/send`, 본문 메시지 배열 최대 100, 헤더 `Content-Type: application/json`, `Accept-Encoding: gzip, deflate`, `EXPO_ACCESS_TOKEN` 이 있으면 `Authorization: Bearer`. 제한 시간 10초.

```ts
message = { to: token, title, subtitle?,   // subtitle 은 IOS 만 (6장)
            body?, sound: 'default', priority: 'high', channelId: 'default',
            data: { url, kind, nid: notificationId },
            expiration?: epoch초 }          // D-98
```

| 결과 | 처리 |
|------|------|
| 200, 티켓 `status: ok` | SENT, `ticketId`, `sentAt = now` |
| 200, 티켓 `DeviceNotRegistered` | FAILED + `PushDevice where token` 삭제 |
| 200, 티켓 `MessageRateExceeded` | QUEUED 로 되돌림 (다음 틱) |
| 200, 티켓 그 밖 오류 (`MessageTooBig`, `InvalidCredentials`, `MismatchSenderId`) | FAILED, `error` 기록, `InvalidCredentials`/`MismatchSenderId` 는 error 로그 `push.credentials` |
| 429, 5xx, 연결 실패(요청 전송 전) | 그 묶음을 QUEUED 로 되돌림 |
| 타임아웃, 응답 본문 해석 실패 | FAILED `TIMEOUT` (접수됐을 수 있어 다시 보내지 않음) |

- QUEUED 로 되돌린 행이 `attempts >= 3` 이거나 알림 예약 시각이 10분 넘게 지났으면 FAILED `EXPIRED`
- Expo 제한(프로젝트당 초당 600건)은 지금 규모에서 닿지 않는다. 묶음 사이 지연은 두지 않는다

### 5-7 영수증
- 틱마다 `status = SENT AND receiptCheckedAt IS NULL AND sentAt <= now - 15분 AND sentAt >= now - 23시간` 최대 1000개 → `POST https://exp.host/--/api/v2/push/getReceipts { ids }`
- `ok` → `receipt = 'ok'`. 오류 → `receipt = 코드`, `DeviceNotRegistered` 면 그 토큰 기기 삭제. 응답에 없는 id 는 `receipt = 'missing'`
- 모두 `receiptCheckedAt = now`

### 5-8 청소 (하루 한 번)
- `PushNotification where createdAt < now - 30일` 삭제 (PushDelivery Cascade) (D-99)

### 5-9 주간 요약과 조용한 팀 깨우기 (`WeeklyPlanner`, #277, D-203 ~ D-205)

기획 3-8. 새 `PushKind.WEEKLY` 하나, 변형 `payload.variant = 'SUMMARY' | 'NUDGE'`. 팀마다 1건 (접근 A).

**예약 (틱 안, 4-1단계)**
```
monday = weeklyDue(now, weekly.dailyDoneOn)   // 지금이 월요일 09:00 ~ 12:00 KST 이고 그 월요일을 아직 안 했으면 그 날짜
없으면 끝
groupIds = Group where memberships some { notify AND user (WEEKLY 켬 OR WEEKLY_NUDGE 켬) AND pushDevices some }
createMany skipDuplicates  { kind WEEKLY, dedupeKey W:{groupId}:{monday}, scheduledAt monday 09:00 + (groupId % 600)초, payload 없음 }
SchedulerLease 'weekly'.dailyDoneOn = monday   // 행이 없으면 upsert
```
- 임대는 'push' 행이 잡고 같은 틱에서만 돈다. 'weekly' 행은 날짜 표시용 (마이그레이션이 넣는다)
- 창 (lo, hi] 을 쓰지 않는 이유: 창 아래 끝이 `now - 10분` 이라 서버가 09:00 ~ 09:10 에 멈춰 있으면 그 주가 통째로 빠진다
- 표시를 적기 전에 죽어도 다시 예약할 때 dedupeKey 가 막는다. 12:00 넘어 돌아오면 그 주는 건너뛴다

**펼치기 (5-6 A 안, WEEKLY 만)**
- 늦음 허용 **3시간** (`WEEKLY_CATCH_UP_MS`). 다른 종류는 10분 그대로 (D-88). 다시 보내기(MessageRateExceeded)의 EXPIRED 판정도 같은 값
- 펼치는 순간의 DB 로 변형과 문구를 정한다 (CHANGE 와 같은 방식). 받는 사람은 변형의 토글로 고른다 (5-6 표). **판정이 "보내지 않음" 이거나 받는 사람이 0명이면 CANCELLED** (깨우기 4주 간격을 쓰지 않는다)
- 새 소식(EventLog) 에는 아무것도 쓰지 않는다

**변형 판정 (팀 하나)**
1. N = 팀 일정 회차 중 이번 주 [월요일 00:00, 다음 월요일 00:00) KST 와 겹치는 수. 반복은 `expand()`(취소 회차 제외, 예외 제목), 여러 날 일정은 이어져도 1개, 참여자(#248)와 무관하게 팀 전체
2. N >= 1 → SUMMARY
3. N = 0 이고 아래를 모두 만족 → NUDGE (싼 조건부터 본다)
   - 팀 종류 TEAM, 지금 멤버 2명 이상, `Group.createdAt` 이 14일 넘게 전
   - [월요일 - 14일, 월요일) 과 겹치는 회차 0, `EventLog CREATED` 가 now - 14일 뒤로 0
   - 이전 3번의 월요일 안에 보낸 NUDGE 없음: `PushNotification where groupId, kind WEEKLY, status DISPATCHED, payload.variant = 'NUDGE', scheduledAt >= 월요일 00:00 - 21일`. 4주에 1번 (보존 30일, D-99 안)
   - 마지막 일정 생성(`max(Event.createdAt)`, 없으면 `Group.createdAt`) 이 90일 안
   - 이번 주 빈 시간 1개 이상: 빈 시간 찾기와 같은 계산(멤버들의 모든 팀 일정, #248 참여자, 종일 제외 D-12, D-14) 을 `from = 지금을 30분 경계로 올림`(D-30), `to = 다음 월요일 00:00`, 09:00 ~ 23:00, 최소 120분으로
4. 그 밖 → 보내지 않음 (CANCELLED)

- 데이터는 `PushRepository` 가 읽고 계산은 순수 함수(`weekly-planner.ts`, `recurrence.expand`, `free-slots/slots.findFreeSlots`, `free-slots/participants.isBusyForAny`) 로 한다 (D-205)
- 규모: 월요일 아침 팀 수만큼 회차 펼치기, 깨우기 후보(TEAM, 2명 이상, 14일 넘음, 회차 0)만 빈 시간 계산. 10분 흩뿌림 + 틱당 500건 펼치기로 수천 팀까지. 1만 팀을 넘으면 틱당 상한이나 일요일 밤 미리 계산 (위험 R-W1)

## 6. 알림 문구 (`push-copy.ts`, D-95)

공통:
- 시각은 KST, `오전/오후 h:mm` (0시 = 오전 12:00, 12시 = 오후 12:00, 웹 `meridiem` 규칙). 날짜는 `M월 D일 (요일)`, 올해(KST)가 아니면 `YYYY년` 앞에 붙임 (웹 `formatDateKo`, `newsDateLabel` 규칙)
- **팀 이름**: IOS 는 `subtitle = 팀 이름`, ANDROID 는 `title = "[팀 이름] " + title`. PERSONAL 팀도 그 이름("내 달력")
- **메모는 넣지 않는다.** 일정 제목, 기념일 이름, 사람 이름, 시각만
- 사람 이름 = 그 팀의 표시 이름(`Membership.displayName ?? User.nickname`), 팀을 나갔으면 닉네임, 탈퇴했으면 "탈퇴한 멤버"
- `이에요/예요` 는 끝 글자 받침으로 (웹 `lib/text.ts` 규칙: 한글이 아니면 받침 없음 쪽)

| 종류 | title | body | data.url |
|------|-------|------|---------|
| REMINDER 시간 | `{제목}` | `AT_START` "지금 {시각}", `MIN_10` "10분 뒤 {시각}", `HOUR_1` "1시간 뒤 {시각}", `DAY_1` "내일 {시각}" | 일정 상세 (아래) |
| REMINDER 종일 | `{제목}` | 하루짜리: `DAY_OF_0900` "오늘 종일", `DAY_BEFORE_0900` "내일 종일". 여러 날: "오늘부터 {끝 날짜}까지" / "내일부터 {끝 날짜}까지" | 일정 상세 |

| JOIN | `{이름}님이 '{팀 이름}' 에 들어왔어요` | 없음 | 팀 달력 |

| POLL 정함 (#189) | `{이름}님이 '{제목}' 시간을 정했어요` | `{날짜} {시각 또는 "종일"}` | 그 일정 상세 |
| NOTICE (#528) | `{공지 제목}` (팀 이름 없음: iOS 부제, Android 앞머리 없음) | 본문의 첫 줄(빈 줄 건너뜀, 앞뒤 공백 자름), 80자를 넘으면 79자 + `…`. 본문이 비면 없음 | 공지 상세 `/notices/{id}?from=push` ((#544) 읽은 경로 push 로 기록, D-293. 옛 경로 `/notices/{id}` 도 열린다) |
| WEEKLY NUDGE (#277) | `2주 동안 같이 잡은 일정이 없어요` | `이번 주 다 같이 비는 시간: {요일} {시작}~{끝}` (+ 더 있으면 ` 외 {k}개`) | 빈 시간 찾기 |

- JOIN 은 문장에 팀 이름이 있어 IOS subtitle, ANDROID 앞머리를 붙이지 않는다
- 늦게 보낸 일정 알림(10분 안 따라잡기)도 문구는 고른 값 그대로 ("1시간 뒤")
- (#277) WEEKLY 의 요일은 KST 한 글자(월 ~ 일), 기념일 꼬리만 "금요일은" 처럼 요일을 붙인다 ("금은" 이 어색해서). 숫자와 사실만, 권유형("~해 보세요", "놓치지 마세요"), 홍보, 혜택 문구 금지 (D-204). `variant` 는 payload 에만 두고 Expo 메시지에는 싣지 않는다

**경로** (`data.url`, 웹 경로만. 셸이 `WEB_ORIGIN` 을 붙인다):

|------|------|
| 일정 상세 | (#311) `/events/{일정 publicCode}?team={팀 publicCode}` + 반복이면 `&occurrence={원래 회차 날짜}` (웹 `eventHref` + `withTeam`. 날짜는 웹이 일정에서 안다). #311 전에 보낸 `/g/{groupId}/calendar?date=&day=1&event=` 는 웹이 308 로 같은 곳에 맞춘다 |

**expiration** (D-98): REMINDER = 회차 시작(종일은 그날 끝 KST 24:00) 이 지나면 의미 없음 → `max(회차 시작, now + 10분)`. ANNIVERSARY = 보내는 날 KST 24:00 (하루 전, 일주일 전도 보낸 날 안에만. "내일은" 이 틀린 말이 되지 않게). CHANGE, JOIN = now + 24시간. WEEKLY = 그 주 월요일 KST 24:00 (#277).

### 8-1 권한 안내 시트 (기획 3-5, D-82)

- 띄우는 때 (둘 중 먼저 오는 것, 한 번만): ① 일정 저장 성공 직후 ② 알림 행에서 "없음" 이 아닌 값을 처음 고를 때
- 조건: `appSupportsPush()` 이고, `pushStatus.permission == 'undetermined'` 이고, `localStorage.wwm_push_prompt` 가 없을 때
- 문구: "약속 전에, 팀원이 일정을 바꿀 때 알려 드릴까요?" [알림 받기] [나중에]
- [알림 받기] → `wwm_push_prompt = 'accepted'`, `pushRequest` → 허용이면 등록 (2-3). 거부면 아무 안내 없이 닫음
- [나중에], 바깥 눌러 닫기 → `wwm_push_prompt = 'later'`. 다시 묻지 않는다 (내 정보 > 알림 에서 켤 수 있다)
- 이미 OS 에서 허용/거부한 기기(`permission != 'undetermined'`)는 시트를 띄우지 않는다
- 기록은 기기(웹뷰 저장소) 단위. 앱을 지웠다 깔면 다시 물을 수 있다

## 15. (#189) 약속 투표 알림

`PushKind.POLL` 하나에 세 단계(열림, 정함, 마감). 문구는 예약할 때 만들고 받는 사람은 펼칠 때 투표 대상에서 고른다. 마감은 30초 틱 안 `PollPlanner` 가 `status = OPEN AND deadline <= now AND deadlineNotifiedAt IS NULL` 을 집어 조건부로 표시하며 예약 시각 = 마감으로 만든다(10분 넘게 늦으면 SKIPPED, D-88). 정하기는 팀원 변경(CHANGE) 대신 정함 1건만 보낸다 (D-236). 자세한 것은 설계 `약속-투표.md` 6장, D-241

## 16. (#528) 공지 푸시 (D-287)

관리자가 공지를 게시할 때 "푸시로도 알리기" 를 고르면 전체 사용자에게 한 번 보낸다. 기존 파이프라인(예약 → 30초 틱 펼치기 → 기기별 발송)을 그대로 쓴다.

| 항목 | 내용 |
|------|------|
| 스키마 | `Notice.pushedAt DateTime?`, `NotificationPreferenceKind.NOTICE`(기본 켬), `PushKind.NOTICE`, `AdminActionType.notice_push`, `PushNotification.groupId` 를 null 허용(NOTICE 만 null). 마이그레이션 `20261125095402_notice_push` |
| 예약 | `POST/PATCH /admin/notices` 의 `push: true` (api.md 2.16). 같은 트랜잭션에서 `pushedAt = 지금` (`pushedAt IS NULL AND publishedAt IS NOT NULL` 조건부) + `PushNotification { kind NOTICE, dedupeKey N:{id}, groupId null, scheduledAt 지금, payload 없음 }`. 커밋 뒤 `PushScheduler.kick()` (합류와 같이, D-91). 요청 안에서 기기로 보내지 않는다 |
| 펼치기 | 펼치는 순간의 공지로 문구를 만든다(그 사이 고친 제목, 본문). 공지가 지워졌거나 게시 취소됐으면 SKIPPED |
| 받는 사람 | `User where pushDevices some AND preferenceOn('NOTICE')` 의 모든 기기. 사용자 id 순으로 1000명씩 이어 읽는다(`NOTICE_RECIPIENT_PAGE`). 팀 설정 `Membership.notify` 는 팀 알림용이라 보지 않는다. 탈퇴한 사용자는 행이 없다(기기 Cascade). 관리자 자신도 켜 두었으면 받는다 |
| 나눠 보내기 | 기기별 발송(PushDelivery) INSERT 는 1000행씩(`DELIVERY_INSERT_CHUNK`, 모든 종류 공통). 발송은 기존 그대로 틱마다 최대 1000건(`SEND_LIMIT`)을 100개 묶음으로 Expo 에 보낸다. 3만 기기면 약 15분(30틱)에 걸쳐 나간다 |
| 늦음 허용 | 3시간 (`WEEKLY_CATCH_UP_MS` 와 같은 값). 시각을 다투지 않고, 전체 대상이라 나눠 보내는 동안 다시 보내기(MessageRateExceeded)가 10분 기준으로 EXPIRED 되지 않게 |
| 만료 | 보낸 때 + 24시간 |
| 방해 금지 | 다른 종류와 같이 없다(3-4, OS 에 맡김) |
| 앱 | 누름 처리는 `data.url` 이 안전한 상대 경로면 그대로 웹뷰로 연다(9장 `notificationTarget`). `/notices/{id}` 는 로그인 없이 열리는 공개 화면이라 세션이 끝났어도 보인다. 앱 업데이트 없이 1.1.0 이상에서 동작 |
| 설정 화면 | 내 정보 > 알림 맨 아래 "공지" (새 기능, 점검 같은 언제볼까 소식을 알려 드려요) |
