# 이메일 로그인 설계

- 이슈: #245 (기획 `docs/기획/이메일-로그인.md`, 2026-11-11 승인)
- 상태: 설계 승인 (2026-11-11). 스키마는 GATE 3 대상
- 결정기록: D-110 ~ D-120
- 공통 규칙(응답 봉투 `{ status, data, message, error? }`, Int ID, 날짜 ISO UTC)은 `api.md` 1장 그대로. 이 문서의 `{ data: ... }` 는 `data` 필드의 모양
- 세션 쿠키(`wwm_session`), `safeNext`, 초대 자동 합류(`?auto=1` + `iat` 5분)는 `인증흐름.md` 그대로 쓴다. 바꾸지 않는다

## 1. 한눈에

```
[브라우저 또는 앱 웹뷰]                 [웹 (Next, Vercel)]                          [API (Railway 1대)]                [Resend]
 /login → "이메일로 계속하기"
 /login/email  이메일 입력 ── POST /auth/email/request ──► X-Internal-Key, X-Client-IP ──► POST /v1/auth/email/request
                                                                                           횟수 제한(DB 행 수), 이전 것 무효
                                                                                           EmailLoginChallenge 1행 ──────► POST /emails
 "메일을 보냈어요" (코드 6칸) ◄── 200 { cooldownSec } ◄─────────────────────────────────── (발송 실패여도 같은 200)

 (코드) 6자리 입력 ── POST /auth/email/code ──────────────────────────────────────────► POST /v1/auth/email/code
 (링크) 메일의 버튼 → GET /auth/email?token= (확인 화면, 소비 안 함)
        [로그인 계속하기] ── form POST /auth/email/link ───────────────────────────────► POST /v1/auth/email/link
                                                                                           1회 소비 → 기존 계정: JWT
                                                                                                     처음: 가입 티켓
 ◄── 기존: Set-Cookie wwm_session, next 로
 ◄── 처음: Set-Cookie wwm_signup → /login/email/nickname ── POST /auth/email/signup ───► POST /v1/auth/email/signup
                                                                                           User + AuthAccount(EMAIL) + 개인 팀
 ◄── Set-Cookie wwm_session, next 로 (초대면 /join/<코드>?auto=1 → 자동 합류)
```

- 링크는 **그 링크를 연 브라우저**가 로그인된다(요청한 기기와 달라도 된다). 코드는 **코드를 넣은 화면**이 로그인된다(앱 웹뷰, 다른 기기)
- 같은 메일의 링크와 코드는 하나가 쓰이면 둘 다 끝난다 (한 행의 `usedAt`)

## 2. 데이터 모델 (Prisma 초안, GATE 3)

추가만 한다. 기존 컬럼과 행은 바꾸지 않는다.

```prisma
enum AuthProvider {
  KAKAO
  APPLE
  GOOGLE
  NAVER
  DEV
  /// (#245) 이메일 링크/코드 로그인. providerUserId = 정규화한 이메일 (D-110)
  EMAIL
}

/// (#245) 이메일 로그인 메일 1통 = 1행. 링크와 코드, 틀린 횟수, 횟수 제한의 근거, 처음 가입 티켓까지 담는다 (D-111)
/// User 와 FK 없음(가입 전에도 생긴다). 탈퇴 시 같은 email 행을 지운다. 30일 뒤 삭제
model EmailLoginChallenge {
  id              Int              @id @default(autoincrement())
  /// 정규화한 이메일 (trim + 소문자, 191자 이하)
  email           String           @db.VarChar(191)
  /// sha256hex(링크 토큰). 원문은 메일에만 있다
  linkTokenHash   String           @unique @db.Char(64)
  /// HMAC-SHA256(코드 키, `${linkTokenHash}:${code}`) hex. 심사 계정은 REVIEW_CODE 로 같은 식 (D-112, D-118)
  codeHash        String           @db.Char(64)
  /// 틀린 코드 횟수. 5 가 되면 invalidatedAt 을 채운다
  attempts        Int              @default(0)
  expiresAt       DateTime
  /// 링크나 코드로 로그인(또는 가입 티켓 발급)된 시각. 채워지면 링크, 코드 둘 다 끝
  usedAt          DateTime?
  usedVia         EmailLoginVia?
  /// 새로 받아서, 또는 5번 틀려서 무효가 된 시각
  invalidatedAt   DateTime?
  /// 로그인 후 갈 웹 경로 + 쿼리 (sanitizeNext 거친 값, 512자)
  next            String           @default("/") @db.VarChar(512)
  /// HMAC-SHA256(IP 키, 클라이언트 IP) hex. IP 원문은 저장하지 않는다 (D-112)
  ipHash          String           @db.Char(64)
  isReview        Boolean          @default(false)
  sendStatus      EmailSendStatus
  /// Resend 응답 id. 도착 시간을 Resend 로그에서 찾을 때 쓴다
  providerMessageId String?        @db.VarChar(64)
  /// 처음 가입 티켓 sha256hex. 닉네임 제출 때 1회 소비하고 null 로 (D-114)
  signupTokenHash String?          @unique @db.Char(64)
  signupExpiresAt DateTime?
  createdAt       DateTime         @default(now())

  @@index([email, createdAt])
  @@index([ipHash, createdAt])
  @@index([createdAt])
}

enum EmailLoginVia {
  LINK
  CODE
}

enum EmailSendStatus {
  /// Resend 가 받음(2xx)
  SENT
  /// Resend 오류, 시간 초과. 화면은 같다
  FAILED
  /// 심사 계정 (보내지 않음) 또는 개발용 콘솔 출력
  SKIPPED
}
```

| 항목 | 규칙 |
|------|------|
| 이메일 계정 | `AuthAccount(provider: EMAIL, providerUserId: 정규화 이메일, email: 같은 값, rawProfile: null)`. 카카오, 애플 계정과 합치지 않는다(#198) |
| 정규화 | 앞뒤 공백 제거 → 전체 소문자. ASCII 만, `로컬@도메인.최상위` 꼴(class-validator `IsEmail({ allow_utf8_local_part: false, require_tld: true })`), 191자 이하. 점, `+` 는 그대로 둔다(Gmail 별칭을 합치지 않음) |
| 이메일 변경 | 없음. 바꾸려면 탈퇴 후 재가입 (기획 3-5) |
| "살아 있는" 메일 | `usedAt IS NULL AND invalidatedAt IS NULL AND expiresAt > now`. 새 요청이 같은 트랜잭션에서 이전 것을 `invalidatedAt = now` 로 만들어 이메일당 최대 1행 |
| 청소 | 요청을 받을 때마다 `createdAt < now - 30일` 행 삭제 (handoff 와 같은 방식, 배치 없음) |
| 마이그레이션 | enum 값 추가 + 새 테이블. 기존 행 변경 없음 |

## 3. 토큰, 코드, 보안 규칙

| 항목 | 값 |
|------|-----|
| 링크 토큰 | `randomBytes(32)` base64url 43자. 저장은 `sha256hex` |
| 코드 | `randomInt(0, 1_000_000)` 6자리 0 채움. 저장은 HMAC-SHA256. 키 = `HKDF-SHA256(JWT_SECRET, info "wwm-email-code")`. 6자리는 공간이 작아 소금만 친 SHA 는 DB 가 새면 바로 풀리므로 서버 비밀을 섞는다 (D-112) |
| IP 해시 | HMAC-SHA256, 키 = `HKDF-SHA256(JWT_SECRET, info "wwm-email-ip")` |
| 비교 | 해시끼리 `timingSafeEqual`. 심사 코드도 같은 식으로 해시해 비교 |
| 유효 | 15분 (`expiresAt = createdAt + 15분`), 1회. 링크와 코드 중 하나가 쓰이면 끝 |
| 틀린 코드 | 조건부 `updateMany(attempts < 5, 살아 있음) attempts += 1`. 5번째 틀림에서 `invalidatedAt` 채움 → 그 메일(링크 포함)은 무효 (기획 3-1) |
| 소비 | 조건부 `updateMany({ id, 살아 있음 } → usedAt, usedVia)` 한 문장. count 1 인 요청만 이긴다 (D-49 와 같은 방식) |
| 가입 티켓 | 처음 이메일이면 소비 때 `randomBytes(32)` base64url 을 만들어 해시와 `signupExpiresAt = now + 30분` 저장. 원문은 웹이 httpOnly 쿠키 `wwm_signup` 으로만 갖는다 |
| 계정 존재 숨김 | 요청 단계는 User 를 조회하지 않는다. 응답, 시간, 메일 문구가 가입 여부와 무관. 발송 실패도 같은 200 |
| 메일 스캐너 | 링크 GET 은 아무것도 소비하지 않는다. 확인 화면의 버튼(form POST)으로만 소비 (D-113, 6-4) |
| CSRF | 웹의 POST route handler 는 `Origin` 이 자기 오리진과 같을 때만 받는다(아니면 403). API 이메일 엔드포인트는 웹 서버만 부를 수 있다(`X-Internal-Key`, D-115) |
| 로그인 CSRF | 남이 보낸 링크로 남의 계정에 들어가는 것을 줄이려고 확인 화면에 그 링크의 이메일을 가려서 보여 준다(`ki***@gmail.com`) |
| 쿠키 | `wwm_session` 은 기존과 같은 속성(`인증흐름.md` 1장). `wwm_signup`: `HttpOnly; SameSite=Lax; Path=/; Max-Age=1800`, 운영 `Secure`. 로그인 성공 때 `wwm_group` 삭제(다른 계정일 수 있음, `/auth/app` 과 같음) |
| 로그 | 토큰, 코드, 가입 티켓, 이메일 전체를 남기지 않는다. 9-3 |

## 4. API

### 4-1 공통
- 모두 `@Public()`, `Cache-Control: no-store`, 컨트롤러 `auth/email` (`EmailLoginController`)
- **웹 서버 전용** (D-115): 헤더 `X-Internal-Key` 가 `INTERNAL_API_KEY` 와 같아야 한다(`timingSafeEqual`). 다르거나 없으면 403 FORBIDDEN. `INTERNAL_API_KEY` 가 비어 있으면 개발(`NODE_ENV !== 'production'`)에서만 통과, 운영은 503 EMAIL_NOT_CONFIGURED
- 클라이언트 IP 는 웹이 넣는 `X-Client-IP` (Vercel `x-forwarded-for` 첫 값, 없으면 `x-real-ip`). 키가 맞을 때만 믿는다. 없으면 `"unknown"`
- 기능 스위치: `EMAIL_LOGIN_ENABLED !== '1'` 이면 모든 이메일 엔드포인트 503 EMAIL_NOT_CONFIGURED (D-119)
- `client` 필드(`"web" | "app"`)는 웹이 UA(`parseAppUserAgent`)로 정한다. `"app"` 으로 로그인되면 `User.lastAppLoginAt = now` (D-97 지표 분모 유지)

### 4-2 엔드포인트

| 메서드 | 경로 | 요청 | 응답 |
|--------|------|------|------|
| POST | `/auth/email/request` | `{ email, next? }` | `{ data: { cooldownSec: 60, expiresInSec: 900 } }`. 가입 여부, 발송 성공과 무관하게 같음 |
| POST | `/auth/email/link/inspect` | `{ token }` | `{ data: { state: "VALID" \| "EXPIRED" \| "USED" \| "INVALID", emailMasked: string \| null } }`. 소비 안 함. `INVALID` 면 `emailMasked: null` |
| POST | `/auth/email/link` | `{ token, client }` | `{ data: AuthResult }` |
| POST | `/auth/email/code` | `{ email, code, client }` | `{ data: AuthResult }` |
| POST | `/auth/email/signup` | `{ signupToken, nickname, client }` | `{ data: { token, next } }` |

```ts
type AuthResult =
  | { kind: "SESSION"; token: string; next: string }                     // 기존 이메일 계정. token = 세션 JWT
  | { kind: "SIGNUP"; signupToken: string; next: string };               // 처음 이메일. 30분 안에 signup
```

**request** (한 트랜잭션은 3~5 만)
```
1. email 정규화, 검증 (실패 400 VALIDATION_FAILED). next = sanitizeNext(next)
2. 횟수 제한 (D-111). 위반이면 429 EMAIL_RATE_LIMITED, details { reason, retryAfterSec }
   COOLDOWN : 같은 email 의 마지막 행 createdAt 이 60초 안
   HOURLY   : 같은 email 최근 1시간 행 5개 이상 → retryAfterSec = 가장 오래된 행 + 1시간 - now
   IP       : 같은 ipHash 최근 1시간 행 20개 이상
3. 같은 email 의 살아 있는 행 invalidatedAt = now
4. 심사 계정이면(email == REVIEW_EMAIL 이고 심사 설정 유효, D-118) codeHash = H(REVIEW_CODE), sendStatus SKIPPED
   아니면 링크 토큰, 코드 생성
5. 행 insert (sendStatus 는 임시 FAILED)
6. (심사 아니면) MailClient.send — 10초 제한. 2xx 면 sendStatus SENT + providerMessageId 갱신. 실패는 로그만
7. 30일 지난 행 청소. 200
```
- 횟수 제한은 발송 실패 행도 센다. 동시 요청 두 개가 둘 다 통과할 수 있다(최대 1통 초과). 받아들인다

**link / code** (소비)
```
link: linkTokenHash 로 행 → 없으면 400 EMAIL_LINK_INVALID { reason: "INVALID" }
      used → reason "USED", invalidated 또는 만료 → "EXPIRED"
code: 형식 /^\d{6}$/ 아니면 400 VALIDATION_FAILED
      email 의 살아 있는 행(최신 1개) 없음 → 400 EMAIL_CODE_EXPIRED
      HMAC 불일치 → attempts += 1. 5 가 됐으면 invalidatedAt 채우고 400 EMAIL_CODE_LOCKED,
                    아니면 400 EMAIL_CODE_INVALID { attemptsLeft }
공통: 조건부 소비(usedAt, usedVia). count 0 이면 위 상태 오류로 다시 판정
      AuthAccount(EMAIL, email) 있으면 → JWT 발급 → SESSION
      없으면 → 가입 티켓 저장 → SIGNUP
```

**signup**
```
1. nickname trim, 2~20자 (기획 3-3. PATCH /me 의 1~20 은 그대로, D-114). 위반 400 VALIDATION_FAILED
2. signupTokenHash 로 행, signupExpiresAt > now. 없으면 401 SIGNUP_TOKEN_INVALID
3. 조건부 updateMany(signupTokenHash = h, signupExpiresAt > now → signupTokenHash null). count 0 이면 401 SIGNUP_TOKEN_INVALID
4. users.createWithAccountTx({ provider: EMAIL, providerUserId: email, email, rawProfile: null, nickname }, 개인 팀)
   P2002(같은 이메일이 다른 탭에서 먼저 가입) → 그 계정으로 로그인 (닉네임은 무시)
5. JWT 발급 → { token, next: 행의 next }
```
- 사진은 없음(이니셜). 소셜 사진 복사(D-37) 단계를 건너뛴다
- `EmailProvider`(`auth/providers/email.provider.ts`, `unlink` 는 아무것도 안 함)를 `AuthProviders` 에 등록한다. 없으면 탈퇴의 제공자 루프가 500

### 4-3 오류 코드 (api.md 오류 표에 추가)

| code | HTTP | 언제 | message |
|------|------|------|---------|
| EMAIL_RATE_LIMITED | 429 | 4-2 request 2단계. `details: { reason: "COOLDOWN" \| "HOURLY" \| "IP", retryAfterSec }` | "잠시 후 다시 보내 주세요" (웹이 reason 별 문구로 바꿈, 6-6) |
| EMAIL_LINK_INVALID | 400 | 링크 없음, 사용됨, 만료, 무효. `details: { reason: "INVALID" \| "USED" \| "EXPIRED" }` | "로그인 링크를 쓸 수 없어요" |
| EMAIL_CODE_INVALID | 400 | 코드 불일치. `details: { attemptsLeft }` | "코드가 맞지 않아요" |
| EMAIL_CODE_LOCKED | 400 | 5번째 틀림 | "코드를 5번 틀렸어요. 메일을 다시 받아 주세요" |
| EMAIL_CODE_EXPIRED | 400 | 살아 있는 메일 없음 (만료, 사용, 새로 받음, 잠김) | "코드가 만료됐어요. 메일을 다시 받아 주세요" |
| SIGNUP_TOKEN_INVALID | 401 | 가입 티켓 없음, 만료, 사용됨 | "가입 시간이 지났어요. 다시 시작해 주세요" |
| EMAIL_NOT_CONFIGURED | 503 | 스위치 꺼짐, 운영에서 `RESEND_API_KEY` 또는 `INTERNAL_API_KEY` 없음 | "지금은 이메일로 로그인할 수 없어요" |

`EMAIL_CODE_EXPIRED` 와 `EMAIL_CODE_INVALID` 의 차이는 "그 이메일로 15분 안에 누군가 요청했는가" 만 드러낸다. 계정 존재 여부는 드러나지 않는다.

### 4-4 환경 변수 (API, 모두 운영 기동 필수 아님)

| 이름 | 값 | 비면 |
|------|-----|------|
| `EMAIL_LOGIN_ENABLED` | `1` 이면 켬 | 503 EMAIL_NOT_CONFIGURED |
| `RESEND_API_KEY` | `re_...` (Sending access, 도메인 `whenwemeet.day` 한정 키) | 운영 503. 개발은 콘솔 출력 메일러 (D-117) |
| `EMAIL_FROM` | 기본 `언제볼까 <noreply@whenwemeet.day>` | 기본값 |
| `INTERNAL_API_KEY` | 32바이트 랜덤 hex. **웹(Vercel)과 같은 값** | 운영 503, 개발 통과 |
| `REVIEW_EMAIL`, `REVIEW_CODE` | 심사 이메일 1개, 6자리 숫자 | 둘 중 하나라도 비거나 코드가 6자리 숫자가 아니면 심사 기능 꺼짐(기동 때 경고 1줄). 그 이메일은 일반 이메일처럼 동작 |
| `RESEND_API_URL` | 기본 `https://api.resend.com` (e2e 가짜 서버용) | 기본값 |

`WEB_ORIGIN` 으로 링크를 만든다. `JWT_SECRET` 에서 코드, IP 키를 파생하므로 이것을 바꾸면 15분 안의 코드가 무효가 되고 IP 횟수가 초기화된다(무해).

## 5. 메일 (Resend)

| 항목 | 값 |
|------|-----|
| 호출 | `fetch POST ${RESEND_API_URL}/emails`, `Authorization: Bearer ${RESEND_API_KEY}`, `Idempotency-Key: email-login-<challengeId>`, 10초 제한, 재시도 없음 (D-117) |
| 본문 | `{ from: EMAIL_FROM, to: [email], subject, html, text, tags: [{ name: "type", value: "login" }] }` |
| 주입 | `MAIL_CLIENT` 토큰의 `MailClient { send(msg): Promise<{ status: "SENT"; id: string \| null } \| { status: "SKIPPED" }> }`, 실패는 `MailSendError(httpStatus, errorName)` 를 던진다. 구현 `ResendMailClient`, `ConsoleMailClient`(개발, 링크와 코드를 콘솔에, SKIPPED), 테스트는 가짜 |

### 6-4 링크 착지 `/auth/email?token=` (D-113)

메일 스캐너(Microsoft Safe Links, 회사 보안 게이트웨이, 메일 앱 미리보기)는 링크를 GET 으로 미리 연다. GET 에서 소비하면 사용자가 누르기 전에 링크와 코드가 같이 죽는다.

- 서버 컴포넌트가 `inspect` 를 부르고(토큰 형식 `^[A-Za-z0-9_-]{43}$` 아니면 부르지 않고 INVALID), 결과로 화면을 그린다. `metadata.referrer = "no-referrer"`, `robots: noindex`
- `VALID`: 심볼, 제목 "언제볼까 시작하기", 설명 "**ki\*\*\*@gmail.com** 계정으로 계속해요", `<form method="post" action="/auth/email/link">` + 숨은 `token` + [로그인 계속하기] primary xl full. **자동 제출하지 않는다** (JS 를 돌리는 스캐너도 있다)
- `EXPIRED` / `INVALID`: 제목 "링크를 쓸 수 없어요", 설명 "15분이 지났거나 새 메일을 받아서 이 링크는 끝났어요.", [메일 다시 받기] → `/login/email`
- `USED`: 제목 "이미 사용한 링크예요", 설명 "이 링크로 로그인했다면 바로 시작할 수 있어요.", [언제볼까 열기] → `/`, 글자 버튼 "메일 다시 받기"
- POST 실패로 돌아온 `?error=<reason>` 도 같은 화면(토큰 없이)
- 이메일 가리기: 로컬 부분 앞 2자(2자 이하면 1자) + `***` + `@도메인`

### 6-5 next 규칙
- `/login/email?next=` 는 `safeNext`. request 에 그대로 실어 API 가 `sanitizeNext` 로 다시 거른 값을 행에 저장
- 로그인 후 이동은 **행에 저장된 next** (링크를 다른 기기에서 열어도 같은 곳으로). 웹은 받은 next 를 `safeNext` 로 한 번 더

## 7. 앱 (웹뷰) (D-116)

**handoff 가 필요 없는 이유**: 카카오와 애플은 셸의 네이티브 화면에서 로그인하므로 결과를 웹뷰로 넘기는 handoff 가 필요했다. 이메일은 입력, 코드, 닉네임이 **전부 웹뷰 안의 웹 화면**이고, 쿠키를 심는 응답(`/auth/email/code`, `/auth/email/signup`)을 웹뷰 자신이 받는다. `wwm_session` 은 그대로 웹뷰 쿠키 저장소에 들어간다(iOS `sharedCookiesEnabled`, Android 백그라운드 때 `flush`, 앱.md 4.4). 앱 푸시 기기 등록도 웹이 자기 세션으로 하므로(D-80) 그대로 동작한다.

**셸이 막지 않는 것 확인**: 셸은 `/auth/kakao`, `/auth/apple` 이동만 네이티브로 가로챈다(`links/urls.ts`). `/login/email`, `/auth/email/*` 는 웹뷰에서 열린다. 메일 앱에서 링크를 누르면 Safari/Chrome 이 열린다(유니버설 링크는 `/join/*` 만(1.1.x 는 `/g/*` 도), D-54, D-199). 그 브라우저가 로그인되고 앱은 코드로 들어온다(기획 3-1).

**앱 안 `/login`** — 지금은 마운트 때 `login` 메시지로 네이티브 화면을 덮어 웹 버튼이 보이지 않는다. 기획 6장 "앱 새 빌드 없이" 를 지키면서 순서(카카오 → Apple → 이메일)를 맞추려고 셸의 능력을 UA 표시로 나눈다.

| 셸 | 판정 | `/login` 앱 안 동작 |
|----|------|-------------------|
| 이메일 표시 있음 (`eas update` 로 받은 1.1.x, 이후 빌드) | UA 에 ` EmailLogin/1` 토큰 | 지금처럼 자동으로 네이티브 화면. 네이티브 화면 맨 아래에 "이메일로 계속하기"(테두리 버튼). 누르면 셸이 오버레이를 닫고 웹뷰로 `${WEB_ORIGIN}/login/email?next=<next>` 를 연다 |
| 표시 없음 (1.0.x, 업데이트 전 1.1.0) | 토큰 없음 | `EMAIL_LOGIN_ENABLED=1` 이면 자동으로 열지 않고 웹 선택 화면: [카카오 또는 Apple로 계속하기](iOS) / [카카오로 계속하기](Android) `Button primary xl` → `login` 메시지(네이티브 화면), 아래 [이메일로 계속하기] outline → `/login/email`. 스위치가 꺼져 있으면 지금 그대로 |

- UA 토큰은 셸 JS 의 `USER_AGENT_SUFFIX` 에 붙인다: `WhenwemeetApp/1.1.0 (ios) EmailLogin/1`. 웹 정규식 `APP_UA` 는 바뀌지 않는다. 버전 비교 대신 토큰을 쓰는 이유는 OTA 가 네이티브 버전을 바꾸지 않기 때문
- 웹 판정 함수 `appSupportsEmailLogin(ua)` 를 `lib/app-bridge.ts` 에. `/login` 서버 렌더에서 결정
- `reason=expired` 는 두 경우 모두 기존 문구 유지
- 셸 변경(이메일 버튼, UA 토큰, `onEmail(next)` 콜백)은 JS 만이라 스토어 빌드 없이 `eas update --channel production` 으로 1.1.0 에 간다. 1.0.x 는 OTA 를 보내지 않고 웹 선택 화면으로 쓴다
- Android 셸의 네이티브 화면은 카카오 + 이메일, iOS 는 카카오 + Apple + 이메일

## 9. 운영

### 9-1 Resend 도메인 (사용자, Cloudflare DNS)
1. Resend 가입 → Domains > Add domain `whenwemeet.day`, Region **Tokyo (ap-northeast-1)** (한국 수신자와 가까움)
2. Resend 가 보여 주는 레코드를 Cloudflare DNS 에 **그대로** 추가(모두 DNS only, 프록시 끔):
   - DKIM: TXT `resend._domainkey`
   - SPF(반송 처리용 하위 도메인): MX `send` → Resend 가 준 `feedback-smtp.<region>.amazonses.com`(우선순위 10), TXT `send` → `v=spf1 include:amazonses.com ~all`
   - DMARC(없으면): TXT `_dmarc` → `v=DMARC1; p=none;` (Gmail, 네이버 도달률). 루트 도메인의 기존 MX, TXT 는 건드리지 않는다
3. Verify → Verified 확인. Domain settings 에서 Click tracking, Open tracking 끔
4. API Keys > Create: 권한 Sending access, Domain `whenwemeet.day`. 값은 Railway 에만

### 9-2 변수
| 위치 | 이름 |
|------|------|
| Railway (api) | `EMAIL_LOGIN_ENABLED=1`, `RESEND_API_KEY`, `INTERNAL_API_KEY`, `REVIEW_EMAIL`, `REVIEW_CODE` (`EMAIL_FROM` 은 기본값) |
| Vercel (web, Production) | `EMAIL_LOGIN_ENABLED=1`, `INTERNAL_API_KEY`(API 와 같은 값) |

켜는 순서: API 배포 + Railway 변수 → 웹 배포 + Vercel 변수(버튼 노출) → 셸 `eas update`. 끌 때는 Vercel 의 스위치부터.

### 9-3 로그 (`Logger('EmailLogin')`)
- request: `challengeId`, 이메일 **도메인만**, `review`, `sendStatus`, Resend HTTP 상태와 오류 `name`, 걸린 ms
- verify: `challengeId`, `via`, 결과(SESSION/SIGNUP/오류 code)
- 남기지 않음: 이메일 전체, 토큰, 코드, 가입 티켓, IP 원문, Resend 요청 본문

### 9-4 성공 기준 측정 (기획 7장, D-120)
| 지표 | 방법 |
|------|------|
| 1. Play 심사 통과 | 심사 결과 |
| 2-1. 신규 가입 중 이메일 비율 | `AuthAccount` 최근 28일 `createdAt`, provider 별 개수 (DEV 제외) |
| 2-2. 메일 → 로그인 완료율 | `EmailLoginChallenge` 최근 28일, `isReview = false AND sendStatus = SENT` 중 `usedAt IS NOT NULL` 비율. `usedVia` 로 링크/코드 비중. 30일 보관이라 28일 창이 된다 |
| 3. 도착 p95 1분 | Resend 대시보드 Emails 로그의 `sent` → `delivered` 시각 (태그 `type=login`). 웹훅은 들이지 않는다 |

Resend 무료 플랜은 하루 100통, 월 3,000통이다. 하루 발송이 70통을 넘으면 유료 플랜을 검토한다(13장).

## 13. 사용자 준비물 (순서대로)

1. Resend 가입, 도메인 추가와 Cloudflare DNS 레코드, Verify, 추적 끄기 (9-1 1~3)
2. Resend API 키 생성 (9-1 4)
3. `INTERNAL_API_KEY` 값 만들기(`openssl rand -hex 32`) → Railway 와 Vercel 에 같은 값
4. 심사 이메일 1개(예: 받는 함이 없어도 되는 `review@whenwemeet.day`)와 6자리 코드 정하기 → Railway `REVIEW_EMAIL`, `REVIEW_CODE`. 저장소와 문서에는 쓰지 않는다
5. Railway `EMAIL_LOGIN_ENABLED=1`, `RESEND_API_KEY` → Vercel `EMAIL_LOGIN_ENABLED=1` (API 배포 뒤)
6. 운영 웹에서 심사 이메일로 로그인 → 닉네임 → 팀 "심사용" 만들기, 일정 3~4개, 기념일 1개 (스토어-제출.md 3장과 같은 내용)
7. Play Console: 데이터 보안(이메일 주소), 앱 액세스(심사 로그인 정보) 갱신. App Store Connect: 개인정보(이메일 주소) 갱신 (8-3)
8. Resend 플랜의 로그 보관 기간을 확인해 개인정보처리방침 4장 문구에 알려 주기
9. 개인 메일함으로 실제 로그인 한 번(Gmail, 네이버 중 하나 이상), 스팸함 여부 확인
