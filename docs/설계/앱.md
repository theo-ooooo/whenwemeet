- 범위: 앱 인증 API, 웹 `/auth/app`, 애플 로그인(iOS 네이티브, 웹, Android), 탈퇴 시 애플 토큰 폐기, 웹뷰 브리지, 딥링크, Expo 설정 개요

## 1. 전체 그림

```
[앱 셸 (Expo)]                                 [웹 whenwemeet.day]                 [API api.whenwemeet.day]
 LoginScreen
  ├ 카카오 SDK login() ── accessToken ─────────────────────────────────────────► POST /v1/auth/kakao/native
  └ 애플(iOS) expo-apple-authentication ── identityToken, authorizationCode ───► POST /v1/auth/apple/native
    (Android 앱은 애플 로그인 없음, 3.6. 옛 GET /v1/auth/apple?client=app 복귀 경로는 #204 로 삭제)
       ◄────────────── { handoff } (네이티브 두 경로)
 WebView 로드 https://whenwemeet.day/auth/app?h=<handoff>&v=<verifier>&next=/
                                   │ GET /auth/app (route handler)
                                   │ POST /v1/auth/handoff { handoff, verifier } ─► 1회용 소비, 세션 JWT 발급
                                   │ ◄── { token }
                                   │ Set-Cookie wwm_session, 302 next
```

- 셸은 세션 JWT 를 받지 않는다. 셸이 들고 있는 것은 60초짜리 handoff 와 그 짝인 verifier 뿐 (D-44)
- 로그인 이후는 웹 그대로: 쿠키 → `/api/*` 프록시 → Bearer. `인증흐름.md` 3장 변경 없음

## 2. handoff

### 2.1 저장 방식 (D-49)

서명 토큰 + jti 기록이 아니라 **DB 행 하나** 로 둔다. 1회용 보장에 어차피 테이블이 필요하고, 행만 있으면 서명 키 관리가 필요 없다.

| 항목 | 규칙 |
|------|------|
| 토큰 | 32바이트 랜덤 → base64url (43자). 응답과 URL 에만 존재 |
| 저장 | `AuthHandoff.tokenHash = sha256hex(token)`. 원문은 저장하지 않는다 |
| 바인딩 | 발급 요청의 `codeChallenge = base64url(sha256(verifier))` 를 함께 저장. 교환 시 `verifier` 로 대조 (PKCE S256 과 같은 방식) |
| 유효 | 발급 후 60초. `expiresAt = now + 60s` |
| 1회용 | 교환은 `updateMany({ where: { tokenHash, usedAt: null, expiresAt: { gt: now } }, data: { usedAt: now } })` 한 문장. `count == 1` 일 때만 성공. 동시 요청 두 개 중 하나만 이긴다 |
| 청소 | 발급 시마다 `expiresAt < now - 1일` 행 삭제 (Repository 한 메서드). 배치 작업 없음 |
| 탈퇴 | `User` Cascade 로 함께 삭제 |

verifier 는 앱이 로그인 시작 때마다 32바이트 랜덤으로 만들고 메모리에만 둔다. Android 애플 로그인처럼 handoff 가 커스텀 스킴(`whenwemeet://`)을 거치는 경로에서 같은 스킴을 등록한 다른 앱이 handoff 를 가로채도 verifier 가 없어 쓸 수 없다. 네이티브 SDK 경로도 같은 규칙으로 통일한다.

### 2.2 엔드포인트

| 메서드 | 경로 | 인증 | 요청 | 응답 |
|--------|------|------|------|------|
| POST | `/auth/handoff` | 없음 | `{ handoff: string(43), verifier: string(43~128) }` | `{ data: { token } }` 세션 JWT (`인증흐름.md` 1장과 같은 클레임, 30일). 없음, 만료, 사용됨, verifier 불일치는 모두 401 `HANDOFF_INVALID` (어느 것인지 구분해 알려주지 않음) |

- 호출자는 웹 서버(route handler) 뿐이다. 브라우저와 셸이 직접 부르지 않는다
- 응답에 `Cache-Control: no-store`

### 2.3 웹 `GET /auth/app` (route handler, `app/auth/app/route.ts`)

```
1. 쿼리 h, v 형식 확인 (base64url 문자만, 길이). 아니면 302 /login?error=HANDOFF_INVALID
2. POST ${API_URL}/v1/auth/handoff { handoff: h, verifier: v }
3. 성공 → wwm_session 쿠키(인증흐름.md 1장 속성) 설정, wwm_group 삭제, 302 safeNext(next)
   실패 → 302 /login?error=HANDOFF_INVALID (앱 안이면 /login 이 다시 네이티브 로그인을 부른다, 4장)
```

- 응답 헤더 `Referrer-Policy: no-referrer`, `Cache-Control: no-store` (콜백과 동일)
- `next` 검증은 기존 `safeNext` 그대로 (D-41). 초대 링크로 앱이 열린 경우 `next=/join/<code>?auto=1` 이고, 새 JWT 의 `iat` 가 방금이라 확인 없이 합류한다
- `proxy.ts` 의 인증 필요 경로에 `/auth/app` 을 넣지 않는다

## 3. 소셜 로그인

### 3.1 카카오 네이티브 `POST /auth/kakao/native`

| 요청 | `{ accessToken: string(1~512), codeChallenge: string(43) }` |
|------|------|
| 응답 | `{ data: { handoff, expiresIn: 60 } }` |

```
1. GET https://kapi.kakao.com/v1/user/access_token_info  (Authorization: Bearer <accessToken>)
   401 계열 → 401 SOCIAL_TOKEN_INVALID / 그 밖의 실패 → 502 KAKAO_ERROR
2. 응답 app_id 가 KAKAO_APP_ID 와 다르면 401 SOCIAL_TOKEN_INVALID  (다른 앱에서 받은 토큰 차단)
3. KakaoProvider.fetchProfile(accessToken)  ← 지금 웹 콜백이 쓰는 함수 그대로 (/v2/user/me)
4. AuthService.login(KAKAO, profile)  ← 웹 콜백과 같은 upsert (신규면 PERSONAL 팀 생성)
5. handoff 발급 (codeChallenge 저장)
```

- 웹(REST API 키)과 앱(네이티브 앱 키)은 같은 카카오 앱이므로 `app_id` 와 회원번호가 같다. 웹으로 가입한 사람이 앱에서 카카오로 로그인하면 같은 User 다
- 탈퇴 unlink 는 지금 그대로 (Admin 키, `target_id`)
- `KAKAO_APP_ID` 가 없으면 503 `KAKAO_NOT_CONFIGURED` (D-29 와 같은 방식)

### 3.2 애플 공통 검증 (`auth/providers/apple.provider.ts`, D-50)

| 항목 | 규칙 |
|------|------|
| 라이브러리 | `jose` 의 `createRemoteJWKSet(https://appleid.apple.com/auth/keys)` + `jwtVerify`. 키 캐시는 jose 기본(키 교체 시 자동 재조회) |
| 서명 | `RS256` 만 허용 |
| `iss` | `https://appleid.apple.com` |
| `aud` | 경로별로 하나만 허용. 네이티브는 `APPLE_BUNDLE_ID`, 웹과 Android 는 `APPLE_SERVICE_ID` |
| `exp` | 지나면 거절. 시계 오차 허용 60초 |
| `nonce` | 아래 경로별 값과 일치해야 함 |
| 식별자 | `sub` → `AuthAccount.providerUserId` |
| 이메일 | 받지 않는다. scope 에 email 을 요청하지 않고, 토큰에 와도 저장하지 않음 (`email: null`) |
| 이름 | 첫 로그인에만 온다. 있으면 `nickname` 초기값(성 + 이름, 공백 정리, 20자 자름), 없으면 `"새 사용자"`. 기존 사용자에겐 쓰지 않음 (D-36) |
| 프로필 사진 | 없음 (`profileImageUrl: null`) |

**인가 코드 교환은 필수** (D-51). identity token 만 믿지 않고 함께 온 `authorizationCode` 를 `POST https://appleid.apple.com/auth/token` (`grant_type=authorization_code`, `client_id`, `client_secret`) 으로 교환한다.
- 코드는 1회용 5분이라 identity token 재사용(replay) 을 이것으로 막는다
- 교환 응답의 `refresh_token` 을 `AuthAccount.refreshToken` 에, 그때의 `client_id` 를 `providerClientId` 에 저장한다. 탈퇴 시 폐기(3.5)에 필요하다
- 교환 응답의 `id_token` 도 위 표로 검증하고 `sub` 가 요청의 identity token 과 같아야 한다

**client_secret** (토큰 교환과 폐기 공통): ES256 JWT. 헤더 `{ alg: ES256, kid: APPLE_KEY_ID }`, 클레임 `{ iss: APPLE_TEAM_ID, iat, exp: iat + 5분, aud: "https://appleid.apple.com", sub: <client_id> }`, `APPLE_PRIVATE_KEY`(.p8) 로 서명. 요청마다 만든다 (최대 6개월 유효지만 보관하지 않음).

`APPLE_*` 가 하나라도 없으면 애플 엔드포인트 전부 503 `APPLE_NOT_CONFIGURED`. 서버 기동은 막지 않는다.

### 3.3 애플 iOS 네이티브 `POST /auth/apple/native`

| 요청 | `{ identityToken, authorizationCode, nonce: string(32~128), nickname?: string(1~20), codeChallenge }` |
|------|------|
| 응답 | `{ data: { handoff, expiresIn: 60 } }` |

- 앱은 로그인마다 랜덤 `nonce` 를 만들어 Apple 요청에는 `sha256hex(nonce)` 를, API 에는 원문을 보낸다. API 는 토큰의 `nonce` 클레임 == `sha256hex(요청 nonce)` 를 확인한다
- `nickname` 은 `AppleAuthenticationCredential.fullName` 을 앱이 합친 값. 신규 가입일 때만 쓴다
- 순서: identity token 검증(aud = 번들 ID) → 코드 교환(client_id = 번들 ID) → `AuthService.login(APPLE, profile)` + refresh token 저장 → handoff

### 3.4 애플 웹 (웹 브라우저) (D-52)

| 메서드 | 경로 | 인증 | 요청 | 응답 |
|--------|------|------|------|------|
| GET | `/auth/apple` | 없음 | 쿼리 `next?`(카카오와 같은 규칙). 옛 `client`, `cc` 는 #204 로 삭제(보내도 무시) | 302 → `https://appleid.apple.com/auth/authorize?client_id=<SERVICE_ID>&redirect_uri=<APPLE_REDIRECT_URI>&response_type=code&response_mode=form_post&scope=name&state&nonce` |
| POST | `/auth/apple/callback` | 없음 | `application/x-www-form-urlencoded`: `code`, `state`, `id_token`, `user?`(첫 로그인 이름 JSON), `error?` | 아래 |

```
GET /auth/apple
  nonce = 32바이트 hex, state = base64url({ nonce, next })
  Set-Cookie wwm_apple_state=nonce; HttpOnly; Secure; SameSite=None; Path=/v1/auth/apple; Max-Age=600
  Authorize 의 nonce 파라미터 = nonce

POST /auth/apple/callback
  state.nonce == 쿠키 nonce 확인 (아니면 OAUTH_STATE), 쿠키 삭제
  error=user_cancelled_authorize → 오류 코드 APPLE_CANCELLED
  code 교환(client_id = SERVICE_ID) → id_token 검증(aud = SERVICE_ID, nonce == state.nonce)
  user JSON 의 name 으로 nickname (신규만)
  login(APPLE) + refresh token 저장
  성공 → 302 ${WEB_ORIGIN}/auth/callback?token=<JWT>&next=...   (카카오 웹과 동일, D-10)
  실패 → 302 ${WEB_ORIGIN}/login?error=<code>
```

- `scope=name` 이면 Apple 이 `form_post` 를 강제한다. 이 POST 는 `appleid.apple.com` 발 교차 사이트 요청이라 `SameSite=Lax` 쿠키가 실리지 않는다 → state 쿠키만 `SameSite=None; Secure`. 세션 쿠키 정책은 바꾸지 않는다
- 웹 로그인 화면의 애플 버튼은 `app/auth/apple/route.ts` (카카오와 같은 302 한 겹) → `${API_URL}/v1/auth/apple?next=`
- ~~Android 셸은 `expo-web-browser` 의 `openAuthSessionAsync(<API>/v1/auth/apple?client=app&cc=..&next=.., "whenwemeet://auth")` 로 연다 (Custom Tabs, 웹뷰 아님). 돌아온 `h` 와 메모리의 verifier 로 `/auth/app` 을 웹뷰에 연다~~ → #145 로 Android 앱은 애플 로그인을 쓰지 않는다 (3.6). API `client=app` 경로와 셸 `parseAuthReturn` 은 #204 로 지웠다 (스토어 빌드 1.0.0, 1.1.0 은 모두 #145 이후라 이 경로를 부르지 않는다)
- Apple 은 `localhost` 반환 URL 을 받지 않는다. 로컬 개발은 dev-login 으로 하고 애플 웹 흐름은 운영 또는 터널 주소로 확인

### 3.5 탈퇴 시 애플 토큰 폐기 (`api.md` 2.7 의 1단계 확장)

```
연결된 AuthAccount 마다 제공자별 unlink (D-34)
  KAKAO: 지금 그대로
  APPLE: POST https://appleid.apple.com/auth/revoke
         client_id = providerClientId, client_secret(3.2), token = refreshToken, token_type_hint = refresh_token
         200 → 성공. 400 invalid_grant → 이미 폐기된 것으로 보고 성공
         refreshToken 이 null(교환 실패 등) → 건너뛰고 경고 로그
         그 밖의 실패 → 502 APPLE_ERROR, DB 는 건드리지 않음 (사용자가 다시 시도)
  DEV: 건너뜀
```

`AuthProviderClient.unlink(providerUserId)` 를 `unlink(account: { providerUserId, providerClientId, refreshToken })` 로 넓힌다. 카카오는 `providerUserId` 만 쓴다.


### 3.6 로그인 화면 모양과 버튼 문구 (#145)
- 셸 네이티브 로그인 화면(`apps/mobile/src/screens/LoginScreen.tsx`)은 웹 `/login` 과 같은 모양: 왼쪽 위 심볼 40, 칩(커플, 가족, 친구 모임, 스터디), 제목 "언제 / 볼까?"(44/700, 줄높이 1, 자간 -0.04em, "?" 는 acc-ink), 설명 15/22, 버튼, 약관 안내 12. 색은 `globals.css` 의 라이트/다크 값(`login-bg`, ink, soft, mute, line, acc-ink, danger)을 `ui/theme.ts` 의 `login` 에 그대로 옮긴다. 여백은 웹과 같고 위는 `max(60, safe-area-top)`, 아래는 `34 + safe-area-bottom`
- 글꼴은 Pretendard(SIL OFL 1.1) 원본 OTF 400, 500, 700 세 개를 `assets/fonts/` 에 넣고 `expo-font` `useFonts` 로 읽는다 (라이선스 전문 동봉, 예약 글꼴 이름 조항 때문에 서브셋하지 않음). 읽기 전이나 실패하면 시스템 글꼴
- 소셜 버튼은 웹 `SocialLoginButton` 과 같은 틀: 높이 48, 모서리 12, 좌우 16, 아이콘 20 칸 + 간격 8, 15/700. 아이콘은 웹 SVG path 를 `scripts/gen-login-icons.mjs` 로 PNG(3배, 흰 단색)로 만들어 `tintColor` 로 칠한다 (react-native-svg 를 넣지 않아 개발 빌드 재생성이 필요 없다)
  - 카카오: 바탕 #FEE500, 심볼 #000000, 글자 #000000 85% (카카오 가이드). 웹 `--color-kakao-ink` 도 같은 값으로 바꿈
  - Apple: 시스템 `AppleAuthenticationButton` 대신 같은 틀의 사용자 버튼 (HIG 의 custom button 허용 범위: 승인된 제목, Apple 로고 왼쪽, 흑/백). 바탕 ink, 글자 bg 로 다크 모드에서 흰 바탕으로 뒤집힌다. 누르면 `signInAsync`
- 문구는 웹과 앱 모두 **"카카오로 계속하기", "Apple로 계속하기"** (Apple 승인 제목 Continue with Apple). 약관 안내는 "계속하면 …에 동의한 것으로 봐요". 초대 화면(`/join/<코드>`)도 같은 두 문구를 쓰고 "합류" 를 버튼에 붙이지 않는다 (승인 제목을 벗어나지 않게, 합류는 화면 설명이 알려 준다). 진행 중 문구 "…로 이동 중…" 은 그대로
- **Android 앱은 애플 로그인을 쓰지 않는다.** 셸 로그인 화면에 애플 버튼이 없고(`loginWithApple` 은 iOS 전용), 앱 셸 안의 웹은 UA `WhenwemeetApp/<버전> (android)` 이면 `APPLE_LOGIN_ENABLED=1` 이어도 애플 버튼을 숨긴다 (`lib/auth.ts` `webAppleEnabled`). iOS 앱과 일반 웹은 그대로

## 4. 웹뷰 브리지 (D-53)

### 4.1 앱 감지

- 셸은 WebView `applicationNameForUserAgent` 에 `WhenwemeetApp/<앱버전> (<ios|android>)` 를 붙인다
- 웹은 `lib/app-bridge.ts` 하나에서만 판정: UA 에 `WhenwemeetApp/` 가 있고 `window.ReactNativeWebView` 가 있을 때 앱. 서버 컴포넌트는 UA 만 본다 (로그인 화면 분기용)
- 앱 판정이 틀려도 기존 웹 동작으로 떨어지게 짠다 (메시지를 보낼 대상이 없으면 웹 방식 그대로)

### 4.2 메시지 (웹 → 셸, `window.ReactNativeWebView.postMessage(JSON.stringify(msg))`)

모든 메시지는 `{ v: 1, type, ... }`. 셸은 목록에 없는 `type`, `v` 불일치, 출처 URL 이 `WEB_ORIGIN` 이 아닌 메시지를 버린다.

| type | 필드 | 보내는 때 | 셸 동작 |
|------|------|----------|--------|
| `login` | `next?: string`, `reason?: 'expired'` | 앱 안에서 `/login` 이 그려질 때 (만료, 로그아웃 후, handoff 실패) | 네이티브 LoginScreen 표시. 성공 시 `/auth/app?...&next=` |
| `logout` | - | 로그아웃 버튼 → `POST /auth/logout` 직전 | 카카오 SDK 토큰 정리. 이후 웹이 `/login` 으로 가며 `login` 이 온다 |
| `accountDeleted` | - | `DELETE /api/me` 성공 직후 | 카카오 SDK 정리, LoginScreen 표시 |

### 4.5 푸시 알림 (앱 1.1.0, #188, `푸시-알림.md` 2-2, 9장)

웹 → 셸 (웹은 UA 버전 `>= 1.1.0` 일 때만 보낸다, D-81):

| type | 필드 | 셸 동작 (`src/push/notifications.ts`) |
|------|------|------|
| `pushStatus` | `id` (1~40자, 제어문자 없음) | `getPermissionsAsync` → 허용이면 `getExpoPushTokenAsync({ projectId })` → 응답 |
| `pushRequest` | `id` | Android 채널 보장 → 이미 허용이거나 `canAskAgain` 이 false 면 창 없이 응답, 아니면 OS 권한 창(iOS alert, sound. 배지 없음) → 응답 |
| `openSettings` | - | `Linking.openSettings()` |

셸 → 웹 응답: `injectJavaScript` 로 `window.dispatchEvent(new CustomEvent('wwm:app', { detail }))`. `detail = { v: 1, type: 'pushStatus', id, permission, canAskAgain, token, platform: 'IOS'|'ANDROID', appVersion }` (`src/bridge/reply.ts`).
- 웹뷰 현재 주소(`onNavigationStateChange`)가 `WEB_ORIGIN` 이 아니면 보내지 않는다 (권한 창 사이에 다른 곳으로 간 경우)
- `token` 은 granted 이고 `Expo(nent)PushToken[...]` 모양일 때만. 토큰 조회는 4초에서 끊고 `null` (웹 대기 5초 안에 답하려고). 얻은 토큰은 실행 동안 메모리에만 둔다
- iOS 임시 허용(provisional, ephemeral)은 `granted`
- (#288, 1.1.1) `denied` + `canAskAgain: true` 는 `undetermined` 로 보낸다. Android 13+ 는 한 번도 묻지 않은 상태를 이렇게 준다. 웹 `canAskPermission` 과 같은 규칙이라 1.1.0(denied 그대로)과 1.1.1 에서 웹 화면이 같다. `denied` 는 다시 물을 수 없을 때만
- 실패(예외)면 답하지 않는다. 웹이 시간 초과로 `null` 처리

| 항목 | 셸 |
|------|----|
| 기동 | `setNotificationHandler` (배너, 목록, 소리 켬, 배지 끔, D-93, D-95), Android 채널 `default` ("알림", HIGH). 권한은 묻지 않는다 (웹 안내 시트에서만, 푸시-알림.md 8-1) |
| 알림 누름 | 기동 시 `getLastNotificationResponse()` + `addNotificationResponseReceivedListener`. `data.url` 을 `notificationTarget`(`safeNext` 규칙, 상대 경로만)으로 검사 → `${WEB_ORIGIN}${path}` 로 웹뷰 이동(navKey 증가). 네이티브 로그인 화면이 떠 있으면 로그인 후 `next` 로. 절대 주소, `//`, 제어문자는 무시 |
| 토큰 서버 전송 | 하지 않는다. 웹이 자기 세션으로 `PUT /me/push-devices` (D-80) |

    imageUrl,         // 초대: `${공유 주소 오리진}/og/join/<code>?by=<표식>` (OG 카드 그대로, 1200×630)
    imageWidth: 1200, imageHeight: 630,

| 어디서 | 동작 |
|--------|------|
| 브라우저 (모바일, 카카오톡 인앱, PC) | 초대 칸이 그려질 때 JS SDK 를 미리 받는다(`t1.kakaocdn.net/kakao_js_sdk/2.8.4/kakao.min.js`, SRI 고정, 다른 화면에서는 받지 않음) → `Kakao.init(NEXT_PUBLIC_KAKAO_JS_KEY)` → `sendDefault`. 키 없음, 로드 실패(8초), 예외 → 지금 동작(Web Share, 없으면 복사) |
| 앱 셸, UA 에 `KakaoShare/1` | `kakaoShare` 전송. 웹뷰 안에서 JS SDK 는 부르지 않는다 (SDK 가 `intent:`, `kakaolink://` 로 이동하는데 셸이 처리하지 않음) |

- iOS `LSApplicationQueriesSchemes` 의 `kakaolink` 는 `@react-native-kakao/core` 플러그인이, Android `<queries><package android:name="com.kakao.talk"/></queries>` 는 `app.config.ts withKakaoTalkQueries` 가 넣는다 (카카오 키가 있는 빌드만)

### 4.7 홈 화면 위젯 (앱 1.2.0, #197, D-187 ~ D-190)

웹이 스냅샷을 만들어 브리지로 넘기고(방식 A), 셸은 기기 안에만 두고 위젯이 그린다. 셸에 세션이나 토큰이 생기지 않는다(D-44). 서버 변경 없음.

```
[웹 AppShell useWidgetSync]                     [셸 WebScreen]                         [위젯]
 GET /groups, 팀마다 /events?from&to, /anniversaries
 buildWidgetSnapshot → fitWidgetSnapshot(16KB)
 postMessage widgetSnapshot ───────────────────► parseWidgetSnapshot (출처, 크기, 모양)
                                                  iOS: updateTimeline (App Group) ───────► WidgetKit 타임라인
                                                  Android: 문서 폴더 JSON + requestWidgetUpdate ► AppWidget (30분마다 다시 읽음)
 logout / accountDeleted ──────────────────────► clearWidget (로그인 안내로 덮기)
```

**스냅샷** (웹 `lib/widget-snapshot.ts`, 셸 `src/widget/snapshot.ts` 가 같은 계약)

```ts
{
  generatedAt: string,                                  // ISO
  groups: { id: number, name: string /*≤20*/, color: number /*멤버 색 순번 0~6, 내 색 (옛 셸 호환, 핑크는 6)*/, c: number /*(#350) 0~7, 새 셸은 이 값 우선*/, code: string /*(#311) 팀 공개 코드 8자, 누름 주소 ?team=*/ }[],   // 내 팀 앞 10개
  days: { date: "YYYY-MM-DD", events: { g: number, title: string /*≤30*/, time: string, c?: number /*(#343, #350) 일정 색 0~7, 자동이면 없음*/ }[] /*≤3*/, total: number }[],  // 오늘(KST)부터 이어진 7일
  anniversaries: { g: number, title: string /*≤40, "처음 만난 날 300일"*/, date: "YYYY-MM-DD" }[]   // 오늘 포함 가까운 순 3개
}
```

| 항목 | 규칙 |
|------|------|
| 날 | KST 오늘부터 7일. 여러 날 일정은 걸친 날마다, 반복은 API 가 펼친 회차 그대로(팀 + `eventKey` 로 한 번만). 하루 앞 3개 + 전체 수 |
| 순서 | 종일(그날을 통째로 걸친 일정 포함) 먼저, 그다음 시작 순(진행 중인 것이 앞), 같으면 제목 |
| `time` | 종일 "종일", 전날 시작해 그날 끝 "~18:00", 그 밖은 시작 "10:00" (KST) |
| 기념일 | 팀마다 `nextOccurrence`(오늘 포함), `compareOccurrence` 순 3개. 이름은 `occurrenceTitle` |
| 넣지 않는 것 | 메모, 장소, 참여자, 만든 사람 |
| 크기 | 브리지 메시지 전체 16,384자 이하. 넘으면 뒤쪽 날부터 뺀다(오늘만으로도 넘으면 보내지 않음). 셸도 16,384자 넘는 메시지와 다른 type 의 4,096자 초과를 버린다 |
| 글자 | 제어문자는 띄어쓰기, 길면 "…" 로 자름(서로게이트 쌍을 자르지 않음). 셸은 제어문자, 길이 위반, 목록에 없는 팀 id, 이어지지 않는 날이 하나라도 있으면 통째로 버린다 |

**보내는 때** (웹 `lib/useWidgetSync.ts`, AppShell 안. 앱 셸이고 UA 에 `Widget/1` 일 때만)
- 첫 화면: 2초 뒤 (마지막 전송이 10분 안이고 같은 KST 날이면 건너뜀)
- 변경 성공 뒤: `lib/api.ts` 가 `/groups` 아래 GET 이 아닌 요청 성공마다 `wwm:widget-dirty` 를 쏘고 2초 모아 한 번. 보내기 전에 화면이 사라지면(팀 나가기 후 이동) 다음 AppShell 이 바로 보낸다
- 앱이 다시 앞으로: 마지막 전송 10분 뒤부터, KST 날이 바뀌었으면 바로
- 재료는 `useWidgetAgenda` (팀마다 요청 2개, 팀 앞 10개). 하나라도 실패하면 보내지 않고 위젯은 이전 스냅샷 그대로. 팀이 0개면 `widgetClear`

- 누름 (#311, D-199): 위젯 전체 → 오늘 첫 일정의 팀(없으면 첫 팀) 달력 그날 상세 `whenwemeet://calendar?date=<오늘>&day=1&team=<팀 공개 코드>`. 기념일 칸 → `whenwemeet://anniversaries?team=<팀 공개 코드>`. 갈 팀이 없으면 `whenwemeet://`(앱만 열림). 스냅샷 `groups[].code` 가 팀 공개 코드(소문자 영숫자 8자, 없으면 스냅샷 전체를 버린다). 셸의 `parseSchemeLink` → `deepLinkToWebUrl`(5.1 커스텀 스킴 화면 주소) → 웹이 `?team=` 으로 팀을 바꾼다

### 4.8 로그인 방법 연결 (#198, D-257, D-282)

내 정보 > 로그인 방법에서 카카오, Apple 을 연결한다(`api.md` 로그인 방법). 웹 브라우저는 OAuth(`/me/link/start` form POST → 연결 티켓)를 쓰지만, 앱 안에서는 셸이 `/auth/kakao`, `/auth/apple` 이동을 네이티브 로그인으로 가로채므로(4.4) 그 경로를 쓰지 않고 브리지로 한다. 이메일 연결은 웹 화면만으로 끝나 앱에서도 같다.

1. 웹(`SignInMethodsScreen`)이 `POST /me/auth-accounts/link-start { provider }` 로 최근 로그인, 이미 연결, 제공자 설정을 먼저 확인한다. 409 REAUTH_REQUIRED 면 네이티브 시트를 띄우지 않고 "다시 로그인" 창
2. 웹 → 셸 `{ v: 1, type: 'linkAccount', id, provider }`. 웹은 120초 기다린다(사람이 카카오톡이나 Apple 시트에서 고르는 동안)
3. 셸(`auth/login.ts nativeLinkCredentials`)이 네이티브 SDK 로그인만 한다. 카카오 `KakaoUser.login()` 의 accessToken, Apple `signInAsync`(scope 없음, nonce 는 원문의 sha256)의 identityToken, authorizationCode 와 원문 nonce. `/auth/*/native` 는 부르지 않는다(셸에 세션 없음, D-44). 시트가 떠 있는 동안 온 다른 `linkAccount` 는 바로 `error`
4. 셸 → 웹 `wwm:app` 이벤트 (웹뷰 현재 주소가 `WEB_ORIGIN` 일 때만, 푸시 응답(`푸시-알림.md` 2-2)과 같은 `sendToWeb`)
5. 웹이 그 기기 세션으로 `POST /me/auth-accounts { provider: 'KAKAO', accessToken }` 또는 `{ provider: 'APPLE', identityToken, authorizationCode, nonce }`. 결과 토스트와 오류 문구는 웹 OAuth 경로와 같다

| 응답 (`detail`) | 뜻 | 웹 |
|------|------|------|
| `{ v: 1, type: 'linkAccount', id, ok: true, provider: 'KAKAO', credentials: { accessToken } }` | 카카오 로그인 성공 | POST |
| `{ v: 1, type: 'linkAccount', id, ok: true, provider: 'APPLE', credentials: { identityToken, authorizationCode, nonce } }` | Apple 로그인 성공 | POST |
| `{ v: 1, type: 'linkAccount', id, ok: false, reason: 'cancelled' }` | 사용자가 시트를 닫음 | 아무것도 띄우지 않음 |
| `{ ..., ok: false, reason: 'unavailable' }` | 카카오 키 없는 빌드, iPhone 이 아님, Sign in with Apple 을 못 쓰는 기기 | "지금은 연결할 수 없어요" |
| `{ ..., ok: false, reason: 'error' }` (웹이 기다리다 그만두면 `timeout`) | SDK 실패, 시트가 이미 떠 있음 | "카카오(Apple) 연결에 실패했어요. 잠시 후 다시 시도해 주세요" |

- 셸은 SDK 응답에서 위 칸만 새 객체로 옮겨 싣고(`bridge/reply.ts buildLinkAccountReply`), 토큰은 로그에 남기지 않는다. 웹도 칸과 길이(API DTO 한도)를 다시 검사한다(`lib/account-link.ts decodeLinkAccountReply`)
- **UA 토큰 `AccountLink/1`**: 토큰 하나가 카카오와 Apple 을 같이 뜻하므로 둘 중 늘 되는 쪽인 카카오를 조건으로, 카카오 네이티브 앱 키가 있는 빌드만 붙인다(`KakaoShare/1` 과 같은 조건). Apple 은 웹이 Android 앱에서 이미 숨기고(#145, `appleEnabled`), iPhone 에서 Sign in with Apple 을 못 쓰는 드문 기기는 셸이 `unavailable` 로 답한다. 토큰이 없는 옛 셸에서는 웹이 카카오, Apple 버튼을 숨긴다
- 카카오 SDK, `expo-apple-authentication` 은 1.2.0 바이너리에 이미 있어 이 셸 코드는 OTA 로 간다(`runtimeVersion: appVersion`). 스토어 빌드 불필요

그 밖의 경로(`/login`, `/auth/*` 중 `/auth/email` 밖, `/api/*`, `/privacy`, `/terms`)는 유니버설 링크 대상에서 뺀다. 앱 미설치면 지금처럼 웹이 열린다.

카카오톡 인앱 브라우저는 유니버설 링크/앱 링크를 타지 않는다 (#154). 그래서 `/join/<code>` 는 앱 셸 밖 모바일 브라우저에서 "앱에서 열기" 를 보여 주고, 카카오톡 안에서는 열자마자 한 번 앱을 부른다 (`apps/web/src/lib/app-open.ts`). 웹 합류 화면은 늘 그대로 두고, 앱이 없으면 웹에 남는다. 스토어 이동은 웹 환경 변수 `APP_STORE_LIVE` 가 켜진 OS 만 (docs/운영/배포.md).

### 5.2 `/.well-known/apple-app-site-association`

`app/.well-known/apple-app-site-association/route.ts` 로 응답한다 (확장자 없는 정적 파일은 Content-Type 이 `application/json` 으로 나간다는 보장이 없어서). 리다이렉트 없이 200, `Content-Type: application/json`, `proxy.ts` 제외.

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["<APPLE_TEAM_ID>.day.whenwemeet.app"],
        "components": [
          { "/": "/join/*", "comment": "초대 링크" }
        ]
      }
    ]
  }
}
```

### 5.3 `/.well-known/assetlinks.json`

같은 방식(route handler, `application/json`).

```json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "day.whenwemeet.app",
      "sha256_cert_fingerprints": ["<EAS 업로드 키 SHA-256>", "<Play 앱 서명 키 SHA-256>"]
    }
  }
]
```

(#271) 웹 환경 변수 `EMAIL_APP_LINK_ENABLED=1` 이면 `components` 끝에 `{ "/": "/auth/email", "?": { "token": "?*" }, "comment": "메일 로그인 링크 (앱 1.1.1~)" }` 를 붙인다 (D-177). AASA 는 앱 버전을 가리지 않아 켜는 순간 1.1.0 이하 iOS 앱도 메일 링크를 받는데, 그 셸은 `/auth/email` 을 몰라 링크를 버린다. iOS 1.1.1 이 대부분에 깔린 뒤 켠다. assetlinks 는 경로가 없어(앱의 intent filter 가 정한다) 바꿀 것이 없다.

`<…>` 값은 코드에 넣지 않고 웹 환경 변수(7장)에서 읽는다. 값이 비어 있으면 두 라우트는 404.

| 웹 | `EMAIL_APP_LINK_ENABLED` | (#271) `1` 이면 AASA 에 메일 로그인 링크 `/auth/email` (iOS 1.1.1 이 퍼진 뒤, D-177) |
| 모바일 | `EXPO_PUBLIC_WEB_ORIGIN`, `EXPO_PUBLIC_API_ORIGIN` | 웹뷰 시작 주소, 네이티브 로그인 API |
| 모바일 | `KAKAO_NATIVE_APP_KEY` | 빌드 시 플러그인과 SDK 초기화 (앱에 들어가는 공개값) |
| 웹 | `NEXT_PUBLIC_KAKAO_JS_KEY` | (#195) 카카오 JavaScript 키 (공개값, 빌드 때 박힘). 없으면 카카오톡 공유 버튼이 OS 공유 시트/복사로 동작 |

- 위 API 값은 운영 기동 필수 목록(`env.validation.ts`)에 넣지 않는다. 없으면 해당 엔드포인트만 503 (D-55)
- `.p8` 원본 파일과 `APPLE_PRIVATE_KEY` 값은 배포 플랫폼 시크릿에만. 저장소, 문서, EAS 에 두지 않는다

## 8. 오류 코드 (api.md 오류 표에 추가)

| code | HTTP | 언제 |
|------|------|------|
| SOCIAL_TOKEN_INVALID | 401 | 카카오 액세스 토큰 무효 또는 `app_id` 불일치, 애플 토큰 서명/iss/aud/exp/nonce 위반, 애플 코드 교환 `invalid_grant`, 두 토큰의 `sub` 불일치 |
| HANDOFF_INVALID | 401 | handoff 없음, 만료, 사용됨, verifier 불일치 (구분 안 함) |
| OAUTH_STATE | - | 리다이렉트 쿼리 전용(카카오와 공유). 애플 state 불일치 |
| APPLE_CANCELLED | - | 리다이렉트 쿼리 전용. 사용자가 애플 화면에서 취소 |
| APPLE_ERROR | 502 | 애플 JWKS 조회, 토큰 교환, 폐기 실패 (`invalid_grant` 제외) |
| APPLE_NOT_CONFIGURED | 503 | `APPLE_*` 미설정 |
| KAKAO_NOT_CONFIGURED | 503 | (기존) + `KAKAO_APP_ID` 미설정 시 `/auth/kakao/native` |

웹 `/login?error=` 문구: `HANDOFF_INVALID` "로그인이 만료됐어요. 다시 시도해 주세요", `APPLE_CANCELLED` 는 문구 없이 화면만, 그 밖은 기존 "로그인하지 못했어요" 문구.

## 9. 스키마 변경 (`schema.prisma`)

- `AuthAccount` 에 `providerClientId String?`, `refreshToken String? @db.Text` 추가 (애플 폐기용. 카카오는 null)
- `AuthHandoff` 모델 신규 (2.1)
- 마이그레이션 이름 `app_auth` (P2 에서 생성, P3 는 컬럼만 사용)

refresh token 은 평문 저장한다. 이 값으로 할 수 있는 일(토큰 갱신, 폐기)은 모두 `.p8` 로 만든 client_secret 이 있어야 하고, 그 키는 DB 밖(배포 시크릿)에만 있다. DB 유출만으로는 쓸 수 없다.

## 11. 테스트 계획

| 단계 | 대상 | 내용 |
|------|------|------|
| P2 | Service 단위 (Repository 목) | 카카오: `app_id` 불일치 401, 토큰 무효 401, 카카오 5xx 502, 정상 시 기존 login 호출. handoff: 발급 후 교환 성공, 두 번째 교환 401, 61초 후 401, verifier 불일치 401 |
| P2 | Repository e2e (실 DB) | `consumeHandoff` 동시 2건 중 1건만 성공, 만료 청소, User 삭제 시 Cascade |
| P2 | 컨트롤러 e2e | native → handoff → `/auth/handoff` → `/me` 200. 카카오 API 는 HTTP 목 |
| P3 | apple.provider 단위 | 테스트용 RSA 키로 만든 JWKS 를 주입해 서명 위조, iss, aud(번들 ID 와 Service ID 뒤바뀜), exp, nonce 위반 각각 거절. client_secret 클레임 형식. 교환 `invalid_grant` 401 |
| P3 | 탈퇴 | 애플 계정 revoke 호출 인자, `invalid_grant` 성공 처리, 실패 시 502 + DB 그대로, refreshToken null 이면 건너뜀 |
| P3 | 웹 콜백 e2e | form_post 본문, state 불일치, 옛 client=app 쿼리는 무시하고 웹 콜백 302 (#204) |
| P4 | 웹 | `/auth/app` 성공/실패 리다이렉트, `.well-known` 두 라우트의 Content-Type 과 값 없음 404, 앱 UA 일 때 `/login` 이 `login` 메시지 전송(앱 밖은 기존 화면) |
| P5 | 셸 단위 (jest-expo) | 메시지 파서(모르는 type, 다른 출처 버림), 허용 도메인 판정, 링크 → 웹뷰 경로 변환, verifier/challenge 생성 |
| P5 | 실기기 | iPhone: 카카오톡 로그인, 애플 로그인, 초대 링크 탭 시 앱 열림. Android: 카카오톡 로그인(애플 버튼 없음, #145), 앱 링크, 뒤로가기, 공유 시트. 공통: 비행기 모드 → 오프라인 화면 → 복구 |
