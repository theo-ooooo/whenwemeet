# 일정 참여자 설계

- 이슈: #248 (기획 `docs/기획/일정-참여자.md`, 2026-11-11 승인)
- 상태: 설계 승인 (2026-11-11)
- 결정기록: D-130 ~ D-142
- 바뀌는 기존 설계: `api.md` 2.3 (EventInput/Event), 2.5 (빈 시간 3번 조회), 2.7 (나가기 2단계), `푸시-알림.md` 5-6 받는 사람 표의 REMINDER 줄, `반복-일정.md` 4장 표 ("이 일정만" 에서 못 바꾸는 필드에 참여자 추가)

## 1. 한눈에

```
Event (반복이면 원본 1행)
  allMembers   true  = "모두" (그 팀 멤버 전체, 나중에 합류한 사람 포함)
               false = 아래 EventParticipant 행의 사람들. 행이 0 이면 "참여자 없음"
  └ EventParticipant (eventId, userId) 0..N     ← 원본에만. EventException 에는 없다 (기획 3-5)
  creatorId    그대로 ("○○님이 추가")
```

| 상태 | 저장 | 빈 시간 | 일정 알림 | 표시 |
|------|------|---------|----------|------|
| 모두 | `allMembers = true`, 행 없음 | 그 팀 멤버 모두 바쁨 | 그 팀 멤버 모두 | 팀원 색 전부 (상한 3색 + 회색) |
| 골라 담기 | `allMembers = false`, 행 1개 이상 | 참여자만 바쁨 | 참여자만 | 참여자 색 |
| 참여자 없음 | `allMembers = false`, 행 0 | 아무도 바쁘지 않음 | 없음 | 회색 `--mute` |

- 개인 팀도 같은 규칙이다(분기 없음, D-132). 개인 팀 멤버는 나 하나라 "모두" 와 "나" 가 같은 뜻
- 참여자는 그 팀의 **현재 멤버** 만 될 수 있다. 나가거나 탈퇴하면 행이 지워진다 (6장)

## 2. 스키마 (GATE 3 대상)

```prisma
model Event {
  // ... 기존 필드
  /// (#248) true 면 "모두": 그 팀 멤버 전체 (동적). false 면 participants 행, 0 이면 "참여자 없음" (D-130)
  /// DB 기본값 true 는 기존 행 이전과 배포 겹침용. 새 일정의 기본 "나" 는 서비스가 정한다 (D-131)
  allMembers   Boolean            @default(true)
  participants EventParticipant[]
}

/// (#248) 일정 참여자 (allMembers = false 일 때만 행이 있다). 반복이면 원본에만 붙는다 (기획 3-5)
model EventParticipant {
  eventId Int
  userId  Int

  event Event @relation(fields: [eventId], references: [id], onDelete: Cascade)
  user  User  @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@id([eventId, userId])
  @@index([userId])
}

model User {
  // ... 기존 관계
  eventParticipations EventParticipant[]
}

model EventLog {
  // ... 기존 필드
  /// (#248) 변경 시점의 참여자 스냅샷 (지표용, D-136). 이 기능 전 로그와 DELETED 는 null
  participantsAll Boolean?
  /// (#248) allMembers = false 일 때의 userId 배열 (오름차순). "모두" 면 null
  participantIds  Json?
}
```

인덱스
- `@@id([eventId, userId])`: 일정 목록, 빈 시간, 알림의 `participants` 중첩 select(`WHERE eventId IN (...)`)를 받는다
- `@@index([userId])`: 나가기 때 `deleteMany({ userId, event: { groupId } })` 와 User FK. 빈 시간은 행 수가 작아(31일 창) 따로 인덱스를 두지 않는다 (D-137)
- `Event` 에는 인덱스를 더하지 않는다

### 2-1 마이그레이션 (`apps/api/prisma/migrations/<ts>_event_participants/migration.sql`)

```sql
-- AlterTable: 기존 행은 DEFAULT true 로 채워진다 = 기존 일정 모두 "모두" (기획 3-7)
ALTER TABLE `Event` ADD COLUMN `allMembers` BOOLEAN NOT NULL DEFAULT true;

-- AlterTable
ALTER TABLE `EventLog` ADD COLUMN `participantsAll` BOOLEAN NULL,
    ADD COLUMN `participantIds` JSON NULL;

-- CreateTable
CREATE TABLE `EventParticipant` (
    `eventId` INTEGER NOT NULL,
    `userId` INTEGER NOT NULL,

    INDEX `EventParticipant_userId_idx`(`userId`),
    PRIMARY KEY (`eventId`, `userId`)
) DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- AddForeignKey
ALTER TABLE `EventParticipant` ADD CONSTRAINT `EventParticipant_eventId_fkey` FOREIGN KEY (`eventId`) REFERENCES `Event`(`id`) ON DELETE CASCADE ON UPDATE CASCADE;
ALTER TABLE `EventParticipant` ADD CONSTRAINT `EventParticipant_userId_fkey` FOREIGN KEY (`userId`) REFERENCES `User`(`id`) ON DELETE CASCADE ON UPDATE CASCADE;
```

**GATE 3 확인 사항**
- 전부 추가(additive) DDL. 기존 컬럼, 인덱스, 데이터 삭제 없음
- **데이터 변경은 하나: `Event.allMembers` 를 `NOT NULL DEFAULT true` 로 추가해 기존 일정 전부(팀, 개인)가 `true` 가 된다.** 별도 `UPDATE` 문은 없다. 개인 팀 일정의 "모두" 는 멤버가 나 하나라 "늘 나" 와 같다 (기획 3-7 "개인 달력 일정은 그대로")
- 이후 `prisma migrate dev` 가 만드는 SQL 과 위가 다르면 생성본을 쓰되 `DEFAULT true` 는 지킨다
- 적용 직후 확인: `SELECT COUNT(*) FROM Event WHERE allMembers = false;` → 0, `SELECT COUNT(*) FROM EventParticipant;` → 0
- 되돌리기: 새 테이블 DROP, 두 테이블의 새 컬럼 DROP (기존 동작으로 돌아간다. 그 사이 만든 참여자 정보만 사라짐)

## 3. API (`api.md` 2.3 변경)

### 3-1 계약

```ts
EventInput += { participants?: 'ALL' | number[] }   // userId 배열. 생성에서 생략 = [요청자], 수정에서 생략 = 그대로
Event      += { participants: { all: boolean, members: Member[] } }
// all = true  → members 는 그 팀 지금 멤버 전원
// all = false → members 는 참여자 (0 이면 "참여자 없음")
// members 순서는 가입순 (Membership.joinedAt, 팀 설정 멤버 목록과 같다). Member = { userId, displayName, color, profileImageUrl }
```

- 목록, 단건, 생성/수정 응답 모두 같은 모양. 반복 회차는 원본 값 (회차마다 같다)
- `members` 는 `MemberResolver` 로 만든다. 참여자는 언제나 현재 멤버라(6장) 회색 "나간 멤버" 가 섞이지 않는다
- `creator` 는 그대로 ("○○님이 추가")
- 응답 크기: 일정마다 멤버 목록이 붙지만 팀 인원이 작아 무시한다 (D-134)

### 3-2 검증 (VALIDATION_FAILED, field `participants`)

| 입력 | 결과 |
|------|------|
| 생략 | 생성: `[요청자]`. 수정: 그대로 (참여자 없음 일정도 그대로 둔다) |
| `'ALL'` | `allMembers = true`, 행 모두 지움 |
| `number[]` 길이 1~50, 양의 정수 | 중복은 합친다. 모두 이 팀의 현재 멤버여야 한다 |
| `[]` | "참여자를 한 명 이상 골라 주세요" (기획 3-1 최소 1명) |
| 멤버 아닌 id 포함 | "이 팀 멤버만 참여자로 고를 수 있어요" |
| `null`, 다른 문자열, 숫자 아닌 원소 | "participants 는 'ALL' 또는 멤버 id 배열이어야 해요" |

- 멤버 검사는 **쓰기 트랜잭션 안에서** `membership.count({ groupId, userId in ids }) === ids.length` 로 한다. 검사와 저장 사이에 그 사람이 나가 고아 행이 생기는 것을 막는다 (D-133)
- 멤버 전원을 하나씩 고른 배열은 `'ALL'` 로 바꾸지 않는다. "모두" 는 나중 합류자까지 포함하는 다른 뜻이다 (D-133)
- 권한은 지금과 같다: 그 팀 멤버면 누구나 (기획 3-1)
- 개인 팀도 같은 검사 (D-132). 웹은 개인 팀에서 줄을 숨겨 늘 생략(= 나)

### 3-3 반복 일정 (기획 3-5, `반복-일정.md` 4장 표에 추가)

| 대상 | `participants` |
|------|----------------|
| 한 번짜리 PATCH | 바꾼다 |
| `scope=this` | 본문에 있으면 400 VALIDATION_FAILED "이 일정만 수정할 때는 참여자를 바꿀 수 없어요" (`repeat` 과 같은 방식) |
| `scope=following`, 첫 회차 | 원본의 참여자를 바꾼다 |
| `scope=following`, 그 뒤 회차 | 새 원본에 본문 값, 없으면 **원본 참여자를 복사** (`allMembers` + 행). 끊긴 원본은 그대로 |
| 한 번짜리 → 반복 켜기 | 같은 행이라 참여자 유지 |

### 3-4 "변경 없음" 판정과 로그 (기획 3-3)

- `isUnchanged` 에 참여자를 더한다: `allMembers` 같고, `false` 면 정렬한 userId 배열이 같아야 같다. 참여자만 바꿔도 **UPDATED** 로그 1건 + 팀원 변경 알림(CHANGE, 지금 규칙 그대로)
- 로그 스냅샷 (D-136): CREATED, UPDATED 는 저장 후 참여자를 `participantsAll`, `participantIds` 에 넣는다. DELETED 는 null. "이 일정만" 로그는 원본 참여자
- `NewsItem` 과 새 소식 문구는 바꾸지 않는다 ("수정했어요")

### 3-5 서비스 구현 메모

- `EVENT_SELECT` 에 `allMembers: true, participants: { select: { userId: true } }`. `EventRow` 에 `allMembers: boolean; participantIds: number[]` (오름차순)
- 순수 함수 `events/participants.ts`
  - `parseParticipants(raw: unknown): 'ALL' | number[] | undefined` (DTO 커스텀 검증과 공용)
  - `resolveParticipants(input, current, requesterId, isCreate)` → `{ allMembers, ids }`
  - `sameParticipants(a, b): boolean`
  - `toParticipantsView(row, resolver)` → `{ all, members }`
- 저장: 생성은 `participants: { create: ids.map(userId => ({ userId })) }`, 수정은 바뀐 경우만 `participants: { deleteMany: {}, create: [...] }` + `allMembers`. 모두 기존 `*WithLogTx` 트랜잭션 안 (검증 포함)
- `MemberResolver` 에 `all(): Member[]` (가입순) 추가. `resolverFor(groupId)` 가 가입순으로 읽는지 확인하고 아니면 정렬

## 4. 빈 시간 찾기 (`api.md` 2.5, 기획 3-2)

규칙: 일정 하나는 **그 일정의 참여자** 만 바쁘게 한다. 응답은 요청 팀 멤버(`memberIds`) 모두가 비는 구간이므로, 일정이 바쁨에 들어가는 조건은

```
isBusyForAny(event, memberIds) =
    event.allMembers                                  // "모두": 그 팀 멤버 전원. 그 팀은 allGroupIds 에 있으므로 memberIds 중 누군가가 그 팀 멤버다
 || event.participantIds.some(id => memberIds.has(id))  // 참여자 중 요청 팀 멤버가 있으면
// 참여자 없음(allMembers false, 행 0) → false
```

쿼리 전략 (DB 조회 수 4번 그대로, D-137)
```
3. once   select 에 allMembers, participants: { select: { userId } } 추가 (title/memo 는 여전히 없음, D-14)
   series 원본 select 에도 같은 두 필드 추가 (참여자는 원본 값이라 회차 펼치기 전에 거른다)
   → once.filter(isBusyForAny), series.filter(isBusyForAny) 후 지금처럼 펼치고 합친다
```

- DB 의 `participants: { some: ... }` 필터 대신 읽고 거르는 이유: 규칙을 순수 함수 하나에 두어 예시 표로 테스트하고(기획 7장 성공 기준 2), 31일 창의 행 수가 작아 더 읽는 비용이 작다. 참여자 select 는 PK `(eventId, userId)` 로 읽는다
- 다른 팀 일정도 같은 함수 (기획 3-2). 응답에는 지금처럼 비는 구간만 (누가 왜 바쁜지 비노출)
- `memberCount` 그대로

예시 (= `free-slots/participants.spec.ts` 표). 요청 팀 A = {엄마, 아빠}, 엄마는 팀 B(엄마, 이모) 에도 소속

| 일정 | 팀 | 참여자 | 바쁨에 들어감 |
|------|----|-------|--------------|
| 아이 병원 | A | 아빠 | 예 |
| 저녁 약속 | A | 모두 | 예 |
| 지난 팀원 일정 | A | 참여자 없음 | 아니오 |
| 이모 미용실 | B | 이모 | 아니오 (A 멤버 아님) |
| 자매 모임 | B | 모두 | 예 (엄마가 B 멤버) |
| 엄마 회식 | B | 엄마, 이모 | 예 |
| 엄마 개인 일정 | 엄마 개인 | 모두(기존) 또는 [엄마] | 예 |

## 5. 일정 알림 (`푸시-알림.md` 5-6, 기획 3-3)

- **받는 사람만 바뀐다.** 예약 계산(5-3), 중복 키, 문구, 시각 규칙은 그대로
- `PushRepository.listRecipients(groupId, kind, excludeUserId, eventId?)`: `kind = REMINDER` 이면 펼치는 순간 그 일정의 `allMembers`, 참여자를 읽어
  - `allMembers` → 지금처럼 그 팀 멤버 전원
  - 아니면 `Membership.userId in 참여자` 를 where 에 더한다. 참여자가 0 이면 받는 사람 0 (DISPATCHED, 발송 0건. 새 상태를 만들지 않는다)
- 설정 조건(`User.notifyReminder AND Membership.notify`)은 그대로 곱한다
- 펼치는 순간의 참여자다: 예약과 펼치기 사이에 참여자를 바꾸면 바뀐 사람에게 간다 (지금 "펼치는 순간의 팀원" 규칙과 같은 결)
- CHANGE(팀원 변경), ANNIVERSARY, JOIN 은 그대로 팀 전체 (기획 3-3)
- `푸시-알림.md` 5-6 표의 REMINDER 줄은 "참여자 (모두면 팀원 모두, 등록자 여부와 무관)" 로 읽는다 (D-138)

## 6. 나가기와 탈퇴 (`api.md` 2.7, 기획 3-6)

- `MembershipsRepository.removeWithGroupPrune` (나가기와 탈퇴가 같이 쓰는 한 단계) 첫 줄에
  `db.eventParticipant.deleteMany({ where: { userId, event: { groupId } } })` 를 넣는다 (`userId` 는 지우는 멤버십의 값). 그 뒤 지금처럼 멤버십 삭제, 빈 팀 삭제
- 탈퇴는 위 단계에 더해 `User` 삭제의 Cascade 로도 지워진다 (개인 팀 일정 포함)
- 참여자가 0 이 된 일정은 그대로 "참여자 없음" (`allMembers = false`, 행 0). "모두" 일정은 남은 멤버로 자연히 줄어든다
- 이 정리는 일정 변경으로 보지 않는다: EventLog, 새 소식, 팀원 변경 알림 없음 (D-139)
- 다시 합류해도 참여자로 돌아오지 않는다 (새 멤버로 시작)

## 7. 웹

### 7-1 타입과 공용 함수 (`lib/types.ts`, 새 `lib/participants.ts`)

```ts
EventInput.participants?: "ALL" | number[]
Event.participants: { all: boolean; members: Member[] }
```

| 함수 | 결과 |
|------|------|
| `participantsOf(ev)` | `ev.participants ?? { all: false, members: [ev.creator] }` (API 가 먼저 나가지 않은 경우 대비) |
| `participantColors(ev)` | 참여자 색 배열 (가입순). 참여자 없음이면 `[]` |
| `barColors(ev)` | 막대용: 0명 → `["var(--mute)"]`, 1~3명 → 그 색, 4명 이상 → 앞 3색 + `"var(--mute)"` (기획 3-4) |
| `splitBackground(colors, dir)` | 색 하나면 단색, 둘 이상이면 같은 폭 단단한 경계 `linear-gradient(to bottom|to right, c1 0 33.3%, c2 33.3% 66.6%, ...)` |
| `participantLabel(ev, meId)` | "나" (나 하나), "민지" (한 명), "민지, 지훈" (두 명), "민지 외 2명" (셋 이상), "모두" (all), "참여자 없음" |

색은 모두 `memberColor()` 를 거친다. 새 색 없음 (디자인규칙 7장)

### 7-2 표시 규칙 (기획 3-4, D-140, D-141)

| 위치 | 지금 | 바뀐 뒤 |
|------|------|--------|
| 폰 달력 칸 점 (`cellDensity`) | 일정마다 등록자 색 점 1개, 최대 3, "+N"(남은 일정 수) | 일정 순서대로 **참여자마다 점**(참여자 없음은 회색 점 1개)을 이어 붙여 앞 3개. 점을 하나도 못 그린 일정이 있으면 "+N"(그 일정 수), 일정은 다 보였지만 참여자 점이 잘렸으면 숫자 없는 "+" |

### 7-3 일정 작성/수정 폼 (`EventFormScreen`, D-142)

- **참여자 줄**: 폰은 시각 블록 바로 아래, 알림 줄 위. PC 2단이면 오른쪽 단 맨 위 (알림, 반복, 메모, 등록자 순 앞). 줄 모양은 알림 줄과 같다: 왼쪽 "참여자", 오른쪽 겹친 아바타(20, 최대 3) + `participantLabel` 14 `--soft` + ›
- 숨김: 개인 팀(`group.type === "PERSONAL"`), "이 일정만" 으로 들어온 수정(`presetScope === "this"`, 반복 줄과 같은 조건)
- 기본값: 새 일정 `[나]`. 수정은 응답 값(`all` → "ALL", 아니면 members 의 userId). 참여자 없음 일정은 줄 값이 회색 "참여자 없음"
- 복사(`copyFrom`): 원본 참여자를 지금 멤버로 걸러 가져오고, 비면 `[나]`. 빠른 추가(QuickAdd)는 줄 없이 기본 `[나]` (본문 생략), "자세히" 로 넘어가면 `[나]`
- **참여자 시트** (`ParticipantSheet`, 알림 시트와 같은 바텀 시트/넓은 화면 대화상자)
  - 첫 줄 "모두" + 보조 13 `--mute` "나중에 들어온 멤버도 포함" + 오른쪽 겹친 아바타
  - 그 아래 멤버 줄(`useGroup(groupId).members`, 가입순): 아바타 28 + 이름(나는 "이름 (나)") + 체크. 높이 52
  - "모두" 를 고르면 개별 체크가 풀리고, 멤버를 체크하면 "모두" 가 풀린다. 아무것도 안 고른 상태에서는 [완료] 를 막고 "한 명 이상 골라 주세요" 13 `--danger`
  - 바로 반영하지 않고 [완료] 로 닫을 때 반영 (여러 명을 고르는 동안 줄이 흔들리지 않게)
- 보낼 때
  - 생성: 팀이면 늘 싣는다(`"ALL"` 또는 배열), 개인 팀은 생략
  - 수정: **바꿨을 때만** 싣는다. 참여자 없음 일정의 제목만 고쳐도 400 이 나지 않게
  - 반복 일정에서 참여자를 바꿨으면 범위 시트가 "이 일정만" 을 막는다 (`onlyFollowing`, 반복 바꿈과 같은 처리). 부제는 "반복이나 참여자를 바꾸면 이 일정만 고칠 수 없어요". `bodyFor("this")` 는 participants 를 싣지 않는다
  - 나가기 확인(`useLeaveGuard`)의 `formSnapshot` 에 참여자를 넣는다
- 서버 400 `participants` 오류는 줄 아래 13 `--danger` 문구 (멤버가 방금 나간 경우 등). 시트를 다시 열면 지금 멤버만 보인다

### 7-4 목 (`mocks/handler.ts`)

`API_MOCK` 의 일정에 `participants` 를 싣고(시드: 기존 = 모두, 새 일정 = 생성자), 생성/수정 3-2 검증, free-slots 의 바쁨 판정을 4장 함수와 같은 규칙으로 바꾼다.
